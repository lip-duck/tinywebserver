## 2. wrk 压测 HTTP QPS

### 正常结果（QPS ~5000）

```
wrk -t4 -c1000 -d10s http://localhost:9000/index.html

  4 threads and 1000 connections
    Latency   52.10ms   29.75ms  105.55ms
    Req/Sec     1.44k     1.18k    2.50k
  53759 requests in 10.07s, 18.20MB read
Requests/sec:   5340.26
```

### QPS 暴跌到 99 的问题

```
Requests/sec:     99.08
```

**根因**：close_callback task 里的检查 `get_channel(fd) != ch` 误杀正常流程。

handle_read parse 成功后 `remove_from_epoll(ch)`，channels_[fd] 仍 = ch。但 close_callback task 执行时，get_channel(fd) 返回 nullptr（因为 wrk 短连接在 task 执行前就关了，handle_read recv=0 已经 deletechannel）。

**修复**：注释掉检查，QPS 恢复到 5000。

```cpp
g_loop->runInLoop([fd, req, ch]() {
    // 【注释掉检查】高并发下 get_channel(fd) != ch 是正常的（wrk短连接）
    // if (g_loop->get_channel(fd) != ch) { return; }
    req->reset();
    ch->setreadevents();
    g_loop->updatechannel(ch);
    ...
});
```

## 4. 多端口监听

### 为什么要多端口

客户端源端口最多 65535 个。单端口最多接 64000 连接。要测更多连接，服务器开多个监听端口，客户端从不同端口连。

20个端口 × 64000 ≈ 128万连接。

### main() 多端口代码

```cpp
int main() {
    g_loop = new eventloop();
    Logger::instance().init("server.log");
    ConnPool::instance().init("localhost", "lip", "123456", "webserver", 8);
    g_pool = new Threadpool(4);

    // 循环监听 20 个端口
    for (int i = 0; i < 20; i++) {
        int listenfd = socket(AF_INET, SOCK_STREAM, 0);
        if (listenfd == -1) { perror("socket"); exit(1); }

        int opt = 1;
        setsockopt(listenfd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));

        int flags = fcntl(listenfd, F_GETFL, 0);
        flags |= O_NONBLOCK;
        fcntl(listenfd, F_SETFL, flags);

        struct sockaddr_in addr;
        memset(&addr, 0, sizeof(addr));
        addr.sin_family = AF_INET;
        addr.sin_port = htons(9000 + i);  // 9000~9019
        addr.sin_addr.s_addr = htonl(INADDR_ANY);

        if (bind(listenfd, (struct sockaddr*)&addr, sizeof(addr)) == -1) {
            perror("bind");
            exit(1);
        }
        if (listen(listenfd, SOMAXCONN) == -1) {
            perror("listen");
            exit(1);
        }

        channel* listen_ch = new channel(listenfd);
        listen_ch->setreadevents();
        listen_ch->setreadcallback([listen_ch]() { handle_accept(listen_ch); });
        g_loop->updatechannel(listen_ch);
    }

    std::cout << "服务器启动，监听 9000~9019 端口" << std::endl;
    g_loop->loop();
    return 0;
}
```

### 压测命令

```bash
# 服务器端
./m7.mysql

# 客户端另开终端
cd ~/tinywebserver
for port in $(seq 9000 9019); do
    ./mul_client 127.0.0.1 $port &
done
wait
```

### 实测结果

```
每个端口约 8000 连接
20个端口共约 16万连接
服务器段错误（竞态问题）
```

## 6. 遇到的问题汇总

### 问题1：QPS 从 5000 暴跌到 99

**现象**：wrk 压测，QPS 只有 99。

**根因**：close_callback task 里 `get_channel(fd) != ch` 检查误杀正常流程。

handle_read parse 成功后 `remove_from_epoll(ch)`，channels_[fd] 仍 = ch。但 wrk 短连接在 task 执行前就关了，handle_read recv=0 已经 deletechannel（channels_[fd]=nullptr）。task 执行时 get_channel(fd)=nullptr != ch，return，不重新注册读事件。wrk 收不到下一个请求的确认，关连接。QPS 暴跌。

**修复**：注释掉检查。

### 问题2：double free / Segmentation fault（已修复）

**现象**：wrk 高并发压测时，服务器偶发 `free(): double free detected in tcache 2` 或 `Segmentation fault`。curl 单请求正常，wrk 一压就崩。

**调试过程**：

1. 先在 `deletechannel()` 和 `close_connection()` 里加 `fprintf(stderr, ...)`，在工作线程任务里打印 `get_channel(fd)` 的值
2. 发现日志 `PARSE_DONE fd=35 ch=(nil)` —— parse 成功后 channels_[35] 就已经是 nullptr
3. **第一个 bug**：`updatechannel()` 里**漏了 `channels_[fd] = ch;`**！handle_accept 创建了 client_ch 并调 updatechannel，但 updatechannel 只做了 epoll_ctl ADD/MOD，没把 ch 存到 channels_ 数组。所以 get_channel(fd) 永远返回 nullptr。

```cpp
// 修复前（漏了！）
void updatechannel(channel* ch) {
    epoll_ctl(epollfd_, op, fd, &ev);
    // 没有 channels_[fd] = ch;
}

// 修复后
void updatechannel(channel* ch) {
    epoll_ctl(epollfd_, op, fd, &ev);
    channels_[fd] = ch;  // 【关键】
}
```

4. 修复第一个 bug 后，日志变成 `PARSE_DONE fd=35 ch=0x...`，但立刻 `double free detected`
5. **第二个 bug**：epoll_wait 一次返回多个事件（EPOLLIN + EPOLLRDHUP）。handle_read 第一次调用 recv=0 → deletechannel + close(fd) + delete ch。events 数组里还有同一个 fd 的另一个事件，handle_read 第二次调用时 ch 已被 delete，访问野指针。

```
epoll_wait 返回 events 数组：
  events[0] = {fd=35, EPOLLIN}
  events[1] = {fd=35, EPOLLRDHUP}  ← 同一个 fd！

for (i=0; i<nready; i++) {
    ch->handle_events();  // events[0]: recv=0 → delete ch
                          // events[1]: ch 已被 delete → use-after-free!
}
```

**修复方案**：handle_read recv=0 后不立即 `delete ch`，只 close(fd) + erase g_http_requests，让 handle_expired → close_connection 统一 delete ch。这样 events 遍历完之前 ch 不会被 delete。

```cpp
// 修复前：立即 delete
if (n == 0) {
    deletechannel(ch);
    close(fd);
    delete req;
    delete ch;  // ← 问题：events 数组里还有这个 fd 的其他事件
    g_http_requests.erase(fd);
    break;
}

// 修复后：只标记，不 delete
if (n == 0) {
    deletechannel(ch);
    close(fd);
    // 不 delete ch 和 req，让 close_connection 统一清理
    g_http_requests.erase(fd);
    break;
}
```

**最终结果**：QPS 8120，0 socket error，稳定运行 10 秒无 crash。

### 问题3：vector 越界（channels_[fd] 越界）

**现象**：
```
vector::operator[]: Assertion '__n < this->size()' failed.
```

**根因**：channels_ 是 `vector<channel*>`，size=65535。高并发下 fd 超过 65535，直接越界。

**修复方向**：用 `unordered_map<int, channel*>` 或动态扩容 vector。

### 问题4：std::vector<char>::back() 断言失败

**现象**：
```
vector<...>::back(): Assertion '!this->empty()' failed.
```

**根因**：HTTP 请求 buffer 为空时调 back()。

**修复**：调 back() 前检查 !empty()。

### 问题5：close_callback task 里 get_channel(fd) = nullptr

**日志**：
```
close_callback task: fd=1005, get_channel=(nil), ch=0x5cacba674120
```

**根因**：wrk 压测时短连接，close_callback task 执行前，handle_read recv=0 已经 deletechannel。

**结论**：检查 `get_channel(fd) != ch` 在高并发下不可靠，会误杀正常流程。

### 问题6：ulimit 修改被拒绝

**现象**：
```
ulimit -n 1048576
-bash: ulimit: open files: cannot modify limit: Operation not permitted
```

**原因**：WSL2 限制。

**解决**：用 prlimit 或改 /etc/security/limits.conf。

## 7. 百万并发真相

### 单机自测的局限

客户端和服务器在同一台机器上时：
- 客户端源端口最多 65535-1024 ≈ 64000 个
- 即使服务器开 20 个端口，客户端也打不开那么多 socket
- WSL2 内存有限，百万连接占几 GB 内核内存

### 零声教育的百万并发架构

```
1台服务器（4G内存 2核CPU）
3~4台客户端（每台 2G内存 1核CPU）
```

- 客户端从不同机器连，源端口不是瓶颈
- 服务器只做 accept + 收发，不做业务
- 调内核参数（fs.nr_open, tcp_tw_reuse 等）

### 真实数据（本机 WSL2）

| 项目 | 数值 |
|------|------|
| 端口数 | 40个（多端口突破源端口限制） |
| **总连接数** | **100万（1,000,000）** |
| WSL 内存 | 8GB + 4GB swap = 12GB |
| QPS（wrk单端口） | **~8000** |
| 平均延迟 | ~107ms |
| 崩溃问题 | **已修复**（updatechannel 漏存 channels_ + events 数组重复事件） |

### 达成百万并发的关键参数

```bash
# 1. WSL2 内存调大（.wslconfig）
# [wslconfig]
# memory=8GB
# swap=4GB

# 2. 文件描述符上限
ulimit -n 1048576

# 3. TCP 缓冲区调到最小（每连接只占 2KB）
sudo sysctl -w net.ipv4.tcp_rmem="1024 1024 1024"
sudo sysctl -w net.ipv4.tcp_wmem="1024 1024 1024"

# 4. epoll watch 上限
sudo sysctl -w fs.epoll.max_user_watches=2000000

# 5. 端口范围 + TIME_WAIT 复用
sudo sysctl -w net.ipv4.ip_local_port_range="1024 65535"
sudo sysctl -w net.ipv4.tcp_tw_reuse=1

# 6. 多端口监听（40个端口突破单端口源端口限制）
# 9000~9039
```

**瓶颈演进**：
- 6.4万：单端口源端口耗尽 → 多端口解决
- 8.8万：epoll_ctl No space left on device → 调大 max_user_watches 解决
- 88万：WSL OOM terminated → 调大 .wslconfig 内存 + 调小 TCP 缓冲区解决
- **100万：成功**

## 8. 语法点详解

### wrk 命令

```bash
wrk -t4 -c1000 -d10s http://localhost:9000/index.html
```

- `-t`：线程数，一般等于 CPU 核数
- `-c`：并发连接数
- `-d`：压测时长

### setsockopt SO_REUSEADDR

```cpp
int opt = 1;
setsockopt(listenfd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));
```

作用：服务器重启时，端口处于 TIME_WAIT 状态，SO_REUSEADDR 允许立即复用。

### htons

```cpp
addr.sin_port = htons(9000 + i);
```

host to network short，把主机字节序转成网络字节序（大端）。

### 多端口监听循环

```cpp
for (int i = 0; i < 20; i++) {
    // 每个端口独立 socket + bind + listen
    // 每个 listenfd 独立 channel + 注册 epoll
}
```

## 9. 面试问答

### 你的服务器能撑多少并发？

> WSL2 单机环境，20个端口同时监听，支撑约 16 万并发连接。wrk 压测单端口 QPS 约 5000，平均延迟 52ms。生产环境用多机部署（N台客户端压一台服务器）+ 调内核参数，可以撑百万级连接。

### 为什么单 Reactor 单线程能撑这么多连接？

> epoll 是 O(1) 的事件通知，不需要遍历所有 fd。主线程只做 accept 和 IO 分发，业务处理丢给线程池。16万连接大部分是空闲的（keep-alive 但没数据），epoll_wait 不返回它们，CPU 占用很低。

### 高并发下遇到过什么问题？

> 两个 bug：
> 1. **updatechannel 漏了 `channels_[fd] = ch`**：handle_accept 创建了 channel 并注册 epoll，但没存到 channels_ 数组。工作线程通过 fd 查找 channel 时永远拿到 nullptr，直接 return，服务器不响应。
> 2. **epoll events 数组重复事件导致 use-after-free**：epoll_wait 一次返回多个事件，同一个 fd 可能同时有 EPOLLIN 和 EPOLLRDHUP。handle_read 第一次调用 recv=0 时 delete 了 channel，但 events 数组里还有这个 fd 的另一个事件，第二次调用时访问野指针。修复：recv=0 后不立即 delete channel，只 close(fd)，让定时器回调统一清理。

### 怎么调优到百万并发？

> 三个层面：
> 1. **内核参数**：调大 ulimit -n、fs.nr_open、tcp_tw_reuse、somaxconn
> 2. **架构**：多 Reactor（main loop accept + sub loop IO），线程池处理业务
> 3. **部署**：多机压测，客户端从不同机器连，解决源端口瓶颈

### QPS 突然暴跌是什么原因？

> 一开始 close_callback 里检查 get_channel(fd) != ch，高并发下 wrk 短连接在 task 执行前就关了，channels_[fd] 已经是 nullptr，检查误杀正常流程，不重新注册读事件，wrk 收不到下一个请求的确认，QPS 从 5000 跌到 99。注释掉检查后恢复。
