## 二、HTTP 协议基础（必须先背）

### 2.1 请求报文格式

```
GET /index.html HTTP/1.1\r\n
Host: 127.0.0.1:9000\r\n
Connection: keep-alive\r\n
User-Agent: Mozilla/5.0\r\n
\r\n
（请求体，GET 请求通常为空）
```

| 部分 | 说明 | 语法 |
|------|------|------|
| 请求行 | 方法 + URL + 版本 | `GET /index.html HTTP/1.1\r\n` |
| 请求头 | 键: 值，每行一个 | `Host: 127.0.0.1:9000\r\n` |
| 空行 | 只有 `\r\n`，请求头结束标志 | `\r\n` |
| 请求体 | 空行之后的数据，GET 通常没有 | （可选） |

**关键语法**：
- 每一行必须以 `\r\n` 结尾（CRLF，回车+换行），不能只用 `\n`
- 请求行三个部分用**单个空格**分隔
- 请求头的键和值之间用**冒号+空格**（`: `）分隔
- 空行是请求头和请求体的分界标志

### 2.2 响应报文格式

```
HTTP/1.1 200 OK\r\n
Content-Length: 12\r\n
Content-Type: text/html\r\n
Connection: keep-alive\r\n
\r\n
<html>Hello</html>
```

| 部分 | 说明 |
|------|------|
| 状态行 | 版本 + 状态码 + 描述，如 `HTTP/1.1 200 OK` |
| 响应头 | 键: 值，每行一个 |
| 空行 | `\r\n`，响应头结束 |
| 响应体 | 空行之后的实际内容（HTML/图片/JSON等） |

### 2.3 必须记住的三个响应头

| 响应头 | 作用 | 示例 |
|--------|------|------|
| `Content-Length` | 响应体的**字节数**，客户端靠这个判断什么时候读完 | `Content-Length: 1024` |
| `Content-Type` | 响应体的类型，决定浏览器怎么渲染 | `text/html`、`image/png` |
| `Connection` | 是否保持长连接 | `keep-alive`（保持）或 `close`（关闭） |

> ⚠️ **Content-Length 必须精确等于响应体的字节数**，否则浏览器会一直等（少了）或者显示乱码（多了）。

### 2.4 常见状态码

| 状态码 | 描述 | 场景 |
|--------|------|------|
| 200 | OK | 请求成功 |
| 400 | Bad Request | 请求格式不对 |
| 403 | Forbidden | 非法路径，拒绝访问 |
| 404 | Not Found | 请求的文件不存在 |
| 405 | Method Not Allowed | 不支持的请求方法 |
| 500 | Internal Server Error | 服务器内部错误 |

### 2.5 常见 Content-Type（根据文件后缀判断）

| 文件后缀 | Content-Type |
|---------|-------------|
| .html / .htm | text/html; charset=utf-8 |
| .txt | text/plain; charset=utf-8 |
| .css | text/css |
| .js | application/javascript |
| .json | application/json |
| .png | image/png |
| .jpg / .jpeg | image/jpeg |
| .gif | image/gif |
| .ico | image/x-icon |
| 未知 | application/octet-stream（浏览器提示下载） |

## 三、粘包/半包问题（状态机存在的意义）

### 3.1 为什么会有粘包/半包？

TCP 是**流协议**，数据像水流一样连续传输，**没有消息边界**。内核只负责把字节流传过去，不管一次发的是一个请求还是半个请求。

### 3.2 半包

一次 `recv` 只读到了**半个请求**：

```
客户端发送：GET /index.html HTTP/1.1\r\nHost: ...\r\n\r\n
服务器 recv 收到：GET /index.html HTT（只收到一半）
```

原因：客户端分两次发，或者内核缓冲区一次只返回了一部分。

### 3.3 粘包

一次 `recv` 读到了**两个请求粘在一起**：

```
客户端发送：请求1 + 请求2
服务器 recv 收到：GET /a.html HTTP/1.1\r\n...\r\n\r\nGET /b.html HTTP/1.1\r\n...
```

原因：客户端连续发了两个请求，内核把它们合并成一次 recv 返回。

### 3.4 解决：有限状态机（FSM）

状态机的核心思想：**记住"解析到哪一步了"**，每次 recv 到新数据，从上次中断的地方继续解析，而不是从头开始。

```
状态流转：
  解析请求行 → 解析请求头 → （解析请求体）→ 解析完成 → 处理请求 → 回到"解析请求行"（长连接时）
```

这就是第3步要实现的核心。

## 四、第1步：固定返回 HTTP 响应

### 4.1 目标

不管客户端发什么，都返回一个固定的 HTTP 响应。用浏览器访问能看到 "Hello World!"。

### 4.2 代码模板（只改 handle_read）

```cpp
void handle_read(channel* ch) {
    int fd = ch->getfd();
    char buf[1024];

    // 第一部分：把客户端发的数据读走（LT模式必须读完，否则死循环）
    while (true) {
        memset(buf, 0, sizeof(buf));
        int n = recv(fd, buf, sizeof(buf), 0);
        if (n == 0) { /* 客户端断开，关闭连接 */ return; }
        if (n < 0) {
            if (errno == EAGAIN) break;  // 数据读完了
            /* 错误，关闭连接 */ return;
        }
    }

    // 第二部分：构造固定的 HTTP 响应
    const char* response =
        "HTTP/1.1 200 OK\r\n"
        "Content-Length: 12\r\n"
        "Content-Type: text/plain\r\n"
        "Connection: close\r\n"
        "\r\n"
        "Hello World!";

    // 第三部分：发送响应
    send(fd, response, strlen(response), 0);

    // 第四部分：关闭连接（Connection: close）
    g_loop->deletechannel(ch);
    close(fd);
    delete ch;
}
```

### 4.3 语法详解：const char* vs char[] vs std::string

这是第1步最核心的语法点，三种写法都能传给 send，但有本质区别：

#### ① const char*（当前代码用的）

```cpp
const char* response = "HTTP/1.1 200 OK\r\n...Hello World!";
```

- `"..."` 叫**字符串字面量**，编译器把这一整串文本放到**只读常量段(.rodata)**，不是栈内存
- `response` 只是一个指针变量，**只存这一大串字符串的首地址**，本身不存内容
- 优点：**不占栈空间**，常量只读、不会意外修改，直接拿到首地址传给 send
- 缺点：不能修改里面的字符（只读，写会段错误）

#### ② char 数组

```cpp
char response[] = "HTTP/1.1 200 OK\r\n...Hello World!";
```

- 会在**栈上开辟一块内存**，把字面量拷贝到栈数组里
- 数组名在传参时会**隐式退化为首元素指针**，传给 send 效果一样
- 优点：可以修改里面的文本
- 缺点：占用栈内存，长报文不推荐（栈溢出风险）

#### ③ std::string

```cpp
std::string response = "HTTP/1.1 200 OK\r\n...";
send(fd, response.c_str(), response.size(), 0);
```

- `std::string` 是 C++ 类，数据存在堆上
- `.c_str()` 返回 `const char*` 首地址给 send
- 优点：方便拼接字符串（动态构造响应）
- 缺点：多一层类封装，简单静态报文没必要

#### 三者在 send 调用上的等价关系

```cpp
// 方案1：char指针
const char* p = "abc";
send(fd, p, strlen(p), 0);

// 方案2：char数组
char arr[] = "abc";
send(fd, arr, strlen(arr), 0);  // 数组名自动转为首地址指针

// 方案3：std::string
std::string s = "abc";
send(fd, s.c_str(), s.size(), 0);
```

传给 send 的时候，**最终全部都要翻译成一块内存的起始指针**。

### 4.4 strlen 的坑

> `strlen` 会找 `\0` 结束符。字符串字面量末尾编译器自动追加 `\0`，现在没问题。
>
> 但 **HTTP 协议本身不依赖 `\0`，只靠 Content-Length**。如果以后返回二进制报文（图片，中间含 `\0`），`strlen` 直接失效，必须用 `.size()` 或手动写死长度。

**不要混淆两个长度**：
- `Content-Length`：**仅仅是响应体长度**
- `strlen(response)`：**整个 HTTP 报文（头部+空行+body）总字节数**

### 4.5 逐行讲解

- **为什么必须读完数据？** LT（水平触发）模式下，如果数据不读走，`epoll_wait` 会每次都返回这个 fd 就绪，导致死循环。必须读到 `EAGAIN`（内核缓冲区空了）为止。
- `\r\n` 是 HTTP 强制的行结束符，不能写成 `\n`。
- `Content-Length: 12`：`"Hello World!"` 正好 12 个字符。
- `Connection: close`：告诉浏览器发完就关连接。
- 空行 `"\r\n"` 是响应头和响应体的分界，不能少。
- 关闭顺序：`deletechannel`（从 epoll 移除）→ `close(fd)`（关闭 socket）→ `delete ch`（释放 Channel 对象）。

### 4.6 测试方法

- 浏览器访问 `http://127.0.0.1:9000`，能看到 "Hello World!"
- `curl -v http://127.0.0.1:9000`，能看到完整响应头

### 4.7 常见坑

| 坑 | 现象 | 解决 |
|---|------|------|
| `\r\n` 写成 `\n` | 有些浏览器不认 | 必须用 `\r\n` |
| Content-Length 算错 | 浏览器一直等或显示乱码 | 精确等于响应体字节数 |
| 空行漏了 | 浏览器把响应体当响应头解析 | 必须有 `\r\n` 空行 |
| 数据没读完 | epoll 死循环 | 读到 EAGAIN 为止 |

## 五、第2步：解析请求行

### 5.1 目标

从客户端发来的请求数据中，解析出请求行的三个部分：方法（GET/POST）、URL（/index.html）、版本（HTTP/1.1）。

### 5.2 请求行格式

```
GET /index.html HTTP/1.1\r\n
```

三个部分用**单个空格**分隔，行尾是 `\r\n`。

### 5.3 sscanf 函数详解

这是第2步最核心的函数，必须彻底搞懂。

#### 函数原型

```cpp
int sscanf(const char* str, const char* format, ...);
```

| 参数 | 说明 |
|------|------|
| `str` | 要解析的**源字符串**（C 风格，以 `\0` 结尾） |
| `format` | **格式控制字符串**，告诉 sscanf 怎么拆分数据 |
| `...` | 可变参数，**接收解析结果的变量地址**（注意是地址，不是变量本身） |

**返回值**：成功解析的字段数量（`int`）。
- 返回 `3` 表示 3 个字段都解析成功
- 返回 `0` 表示一个都没解析出来
- 返回 `EOF`（-1）表示字符串为空或出错

#### 最常用的格式说明符

| 格式符 | 作用 | 对应变量类型 |
|--------|------|-------------|
| `%d` | 读十进制整数 | `int*` |
| `%f` | 读浮点数 | `float*` |
| `%lf` | 读双精度浮点数 | `double*` |
| `%s` | 读字符串（读到**空格/换行/制表符**停止） | `char*` |
| `%c` | 读单个字符（包括空格） | `char*` |
| `%x` | 读十六进制整数 | `int*` |
| `%%` | 匹配一个字面量 `%` | 无 |

#### `%s` 的行为细节（重点，容易踩坑）

1. **自动跳过开头的空白**：`sscanf("   hello", "%s", buf)` → buf = "hello"
2. **读到空白字符就停**：`sscanf("hello world", "%s", buf)` → buf = "hello"
   - 空白字符包括：空格、制表符 `\t`、换行 `\n`、回车 `\r`、换页 `\f`、垂直制表符 `\v`
3. **自动加 `\0`**：解析出的字符串末尾自动加结束符，接收数组必须留 1 字节给 `\0`
4. **限制读取长度**：`%15s` 表示最多读 15 个字符，留 1 字节给 `\0`，防止缓冲区溢出

#### 为什么传数组名（不是 &数组名）

```cpp
char method[16];
sscanf(request, "%s", method);  // ✅ 传 method，不是 &method
```

`method` 是 `char[16]` 数组，**数组名本身就是首元素地址**，所以直接传就行。
如果是 `int` 变量，就必须传地址：`sscanf("18", "%d", &age);`

#### 高级用法

**跳过不想要的字段：`%*s`**
```cpp
sscanf("GET /index.html HTTP/1.1", "%*s %s %*s", url);
// %*s 读了 "GET" 但不保存
// %s  读了 "/index.html" 保存到 url
// %*s 读了 "HTTP/1.1" 但不保存
```

**匹配字面量字符**：格式串里的普通字符要求精确匹配
```cpp
sscanf("ip=192.168.1.1 port=8080", "ip=%s port=%d", ip, &port);
```

**用 `%[]` 读指定字符集**
```cpp
sscanf("/index.html?name=abc", "%[^?]", path);
// path = "/index.html"，遇到 ? 停止
```

#### sscanf vs scanf vs fscanf

| 函数 | 数据来源 |
|------|---------|
| `scanf` | 标准输入（键盘） |
| `fscanf` | 文件流 |
| `sscanf` | 字符串 |

三个函数格式串完全一样，只是数据来源不同。

#### sscanf 的局限（为什么第3步要换状态机）

- **不能处理半包**：请求行被拆成两次 recv 时，sscanf 解析失败
- **不能处理粘包**：一次 recv 收到两个请求时，sscanf 只解析第一个，第二个丢了

### 5.4 代码模板

```cpp
void handle_read(channel* ch) {
    int fd = ch->getfd();
    char buf[1024];
    std::string request;  // 用 string 累积完整请求

    while (true) {
        memset(buf, 0, sizeof(buf));
        int n = recv(fd, buf, sizeof(buf), 0);
        if (n == 0) { /* 断开 */ return; }
        if (n < 0) { if (errno == EAGAIN) break; /* 错误 */ return; }
        request.append(buf, n);  // 累积数据
    }

    // 解析请求行
    char method[16], url[256], version[16];
    int parsed = sscanf(request.c_str(), "%s %s %s", method, url, version);

    if (parsed == 3) {
        // 解析成功，打印验证
        std::cout << "方法: " << method << " URL: " << url << " 版本: " << version << std::endl;
    }

    // 构造响应（用 std::string 动态拼接）
    std::string body = "<html><body><h1>Hello m3 step2!</h1></body></html>";
    std::string response;
    response += "HTTP/1.1 200 OK\r\n";
    response += "Content-Length: " + std::to_string(body.size()) + "\r\n";
    response += "Content-Type: text/html\r\n";
    response += "Connection: close\r\n";
    response += "\r\n";
    response += body;

    // 循环发送（处理 EAGAIN）
    int total = response.size(), sent = 0;
    while (sent < total) {
        int n = send(fd, response.c_str() + sent, total - sent, 0);
        if (n < 0) {
            if (errno == EAGAIN) { usleep(1000); continue; }
            break;
        }
        sent += n;
    }

    // 关闭连接
    g_loop->deletechannel(ch);
    close(fd);
    delete ch;
}
```

### 5.5 新增语法点

#### std::string 累积数据

第1步用 `char buf[1024]`，每次 recv 覆盖 buf。第2步改成 `std::string request`，每次 recv 后 `request.append(buf, n)` 累积。

**为什么要累积？** 一次 recv 可能只读了半个请求，累积起来才能拿到完整请求。

#### std::to_string

把数字转成字符串，拼到 Content-Length 里：
```cpp
response += "Content-Length: " + std::to_string(body.size()) + "\r\n";
```
不用手数字节数了。

#### 循环 send 处理 EAGAIN

非阻塞模式下，`send` 可能只发了一部分（发送缓冲区满了），返回实际发送的字节数。需要循环发送直到全部发完，遇到 EAGAIN 等 1ms 再重试。

### 5.6 常见坑

| 坑 | 现象 | 解决 |
|---|------|------|
| sscanf 解析失败 | parsed < 3 | 检查请求数据是否完整，半包是第3步的事 |
| 浏览器显示空白 | Content-Length 算错 | 用 `body.size()` 自动算 |
| 响应发不全 | 非阻塞 send 只发了一部分 | 用循环发送 |
| `std::to_string` 编译报错 | 编译器太老 | 编译时加 `-std=c++11` |

## 六、第3步：有限状态机（核心，最难）

### 6.1 为什么需要状态机

第2步用 `sscanf` 解析，假设一次 recv 就能收到完整请求。但真实场景中有半包和粘包，sscanf 处理不了。状态机能记住"解析到哪一步了"，每次 recv 从上次中断的地方继续。

### 6.2 状态机设计

#### 四个状态

```cpp
enum ParseState {
    REQUEST_LINE,  // 正在解析请求行：GET /index.html HTTP/1.1
    HEADERS,       // 正在解析请求头：Host: ... / Connection: ...
    BODY,          // 正在解析请求体（POST 才有）
    FINISHED       // 一个完整请求解析完成
};
```

#### 状态流转图

```
         recv 新数据，追加到缓冲区
                ↓
    ┌─── REQUEST_LINE（解析请求行）
    │           │
    │     找到 \r\n，解析成功
    │           ↓
    │    HEADERS（逐行解析请求头）
    │           │
    │     遇到空行（\r\n）
    │           ↓
    │    ┌──────┴──────┐
    │    │             │
    │  有 Content-Length  没有 body（GET）
    │    │             │
    │    ↓             ↓
    │  BODY（收请求体）  FINISHED（解析完成）
    │    │
    │  收够了 Content-Length 字节
    │    ↓
    └── FINISHED（解析完成）
         │
    处理完这个请求后，reset() 回到 REQUEST_LINE
    缓冲区里剩余的数据继续解析下一个请求（处理粘包）
```

#### 关键数据结构

每个连接维护：
- **缓冲区** `std::string buffer_`：累积所有 recv 到的数据
- **当前状态** `ParseState state_`：记住解析到哪一步了
- **解析结果**：method、url、version、headers（请求头键值对）、content_length、body

### 6.3 HttpRequest 类完整代码

```cpp
class Httprequest {
public:
    enum parse_state { REQUEST_LINE, HEADERS, BODY, FINISHED };

    Httprequest() { reset(); }

    // 重置状态，准备解析下一个请求（长连接/粘包用）
    void reset() {
        state_ = REQUEST_LINE;
        method_.clear();
        path_.clear();
        version_.clear();
        headers_.clear();
        content_length_ = 0;
        body_.clear();
        // ⚠️ 注意：buffer_ 不清除！里面可能还有下一个请求的粘包数据
    }

    // 核心函数：追加数据并解析，返回 true 表示一个完整请求解析完成
    bool parse(const char* data, int len) {
        buffer_.append(data, len);  // 1. 追加新数据

        while (1) {                  // 2. 循环解析
            if (state_ == REQUEST_LINE) {
                size_t pos = buffer_.find("\r\n");
                if (pos == std::string::npos) break;  // 数据不够
                std::string line = buffer_.substr(0, pos);
                sscanf(line.c_str(), "%s %s %s", method_buf, path_buf, version_buf);
                method_ = method_buf;
                path_ = path_buf;
                version_ = version_buf;
                buffer_.erase(0, pos + 2);  // 删掉已解析的行（含 \r\n）
                state_ = HEADERS;
            } else if (state_ == HEADERS) {
                size_t pos = buffer_.find("\r\n");
                if (pos == std::string::npos) break;
                std::string line = buffer_.substr(0, pos);
                buffer_.erase(0, pos + 2);

                if (line.empty()) {
                    // 空行 → 请求头结束
                    if (content_length_ > 0) state_ = BODY;
                    else { state_ = FINISHED; return true; }
                } else {
                    // 解析请求头 "Key: Value"
                    size_t colon = line.find(": ");
                    if (colon != std::string::npos) {
                        std::string key = line.substr(0, colon);
                        std::string value = line.substr(colon + 2);
                        headers_[key] = value;
                        if (key == "Content-Length") {
                            content_length_ = std::stoi(value);
                        }
                    }
                }
            } else if (state_ == BODY) {
                if ((int)buffer_.size() < content_length_) break;
                body_ = buffer_.substr(0, content_length_);
                buffer_.erase(0, content_length_);
                state_ = FINISHED;
                return true;
            } else if (state_ == FINISHED) {
                break;
            }
        }
        return (state_ == FINISHED);
    }

    // getters
    const std::string& getmethod() const { return method_; }
    const std::string& getpath() const { return path_; }
    const std::string& getversion() const { return version_; }
    const std::string& getbody() const { return body_; }
    int getcontentlength() const { return content_length_; }
    std::string getheader(const std::string& key) const {
        auto it = headers_.find(key);
        return (it != headers_.end()) ? it->second : "";
    }

    void print() const { /* 打印解析结果 */ }

private:
    parse_state state_;
    std::string buffer_;
    std::string method_, path_, version_, body_;
    std::unordered_map<std::string, std::string> headers_;
    int content_length_;
    char method_buf[16], path_buf[256], version_buf[16];
};
```

### 6.4 parse 函数详解（两个阶段）

```cpp
bool parse(const char* data, int len) {
    buffer_.append(data, len);  // 阶段1：追加新数据
    while (true) {               // 阶段2：循环解析缓冲区
        // 根据当前状态做不同的事
        // 数据不够就 break，等下次 recv
        // 解析完成就 return true
    }
    return (state_ == FINISHED);
}
```

**关键点**：每次调用 `parse()`，先把新数据追加到 `buffer_`，然后从 `state_` 记录的状态继续解析。如果数据不够，就 `break` 退出，`state_` 保持当前状态，下次 recv 后接着来。

#### 各状态详解

**REQUEST_LINE 状态**：
- `buffer_.find("\r\n")`：找第一个 `\r\n`，找到了说明请求行完整了
- `pos == std::string::npos`：没找到，说明半包，退出等更多数据
- `buffer_.erase(0, pos + 2)`：解析完一行就删掉，`+2` 把 `\r\n` 也删掉
- 解析完请求行，状态转 HEADERS

**HEADERS 状态**：
- 逐行解析请求头，每行格式 `Key: Value`
- `line.find(": ")`：找冒号+空格，分割键和值
- 遇到空行（`line.empty()`）说明请求头结束
- 有 Content-Length → 转 BODY；没有（GET）→ FINISHED

**BODY 状态**：
- 请求体没有 `\r\n` 分隔符，靠 Content-Length 知道有多少字节
- 缓冲区数据够了就截取，解析完成

### 6.5 C++ 语法详解：const 成员函数 + 引用返回

这是第3步新增的重要语法，面试高频考点。

```cpp
const std::string& getmethod() const {
    return method_;
}
```

#### 返回值 `const std::string&`

- `&`：**引用返回**，不会拷贝 std::string 对象，直接返回内部成员的内存地址，节省拷贝开销
- `const`：**常量引用**，禁止外部通过返回值修改内部成员
  - ❌ 外部不能写：`obj.getmethod() = "POST";`
  - ✅ 外部只能读，不能改

#### 函数末尾的 `const`（常成员函数，重点！）

```cpp
const std::string& getmethod() const
```

这个 const 表示：调用这个成员函数期间，**不会修改类内任何成员变量**。
- 只能访问成员，不能修改成员
- **const 对象只能调用带末尾 const 的成员函数**

```cpp
const Httprequest req;
std::string m = req.getmethod(); // ✅ 合法，如果函数没有末尾 const，这行编译报错
```

#### ⚠️ 坑点：返回成员引用的生命周期风险

```cpp
HttpRequest foo() {
    HttpRequest r;
    return r;
}
const std::string& ref = foo().getmethod();
// ❗ 危险！foo()返回的临时对象销毁，ref变成野引用！
```

- 安全场景：**只在对象本身存活期间使用这个引用**（绝大多数业务场景没问题）
- 如果不确定对象生命周期，可以改成返回值（会拷贝，牺牲性能换安全）

#### 面试一句话背诵

> 这是类的常量成员 getter 函数，返回成员变量的常量引用。末尾 const 保证函数不修改成员；const 引用避免 string 拷贝，同时防止外部修改内部成员；缺点是调用方拿到的引用依赖对象生命周期，如果对象销毁，引用会失效。

### 6.6 集成到 Reactor

每个连接需要一个 HttpRequest 对象，用全局 map 存储：

```cpp
std::unordered_map<int, Httprequest*> g_http_requests;
```

- `handle_accept` 里：新连接时 `g_http_requests[connfd] = new Httprequest();`
- `handle_read` 里：`g_http_requests.find(fd)` 找到对应对象，调用 `req->parse(buf, n)`
- 断开连接时：`delete req` + `g_http_requests.erase(fd)`

### 6.7 常见坑

| 坑 | 现象 | 解决 |
|---|------|------|
| 解析完一行没 `erase` | 重复解析同一行，死循环 | 每次解析完必须 `buffer_.erase(0, pos+2)` |
| `erase` 时忘了 `+2` | `\r\n` 留在缓冲区，下一行解析出错 | `pos + 2` 把 `\r\n` 也删掉 |
| 请求头分割用 `:` 而不是 `": "` | 值的开头多了一个空格 | 用 `line.find(": ")`，`substr(colon + 2)` |
| `Content-Length` 没转成 int | body 收不够或收多了 | `std::stoi(value)` |
| 新连接没创建 HttpRequest | find 找不到，直接关闭 | handle_accept 里创建 |
| 断开连接没释放 HttpRequest | 内存泄漏 | 断开时 delete + erase |
| GET 请求也进 BODY 状态 | 永远等不到 body，卡住 | content_length_ == 0 时直接 FINISHED |

## 七、第4步：URL 映射到本地文件路径

### 7.1 目标

把解析出的 URL 转换成服务器上的实际文件路径：

| URL | 映射到的文件路径 |
|-----|----------------|
| `/` | `resources/index.html` |
| `/index.html` | `resources/index.html` |
| `/about.html` | `resources/about.html` |
| `/css/style.css` | `resources/css/style.css` |

### 7.2 映射规则

1. **加资源目录前缀**：所有静态资源放在 `resources/` 目录下
2. **默认首页**：URL 是 `/` 时映射到 `index.html`
3. **防止路径穿越**：URL 包含 `..` 时拒绝（安全问题）

### 7.3 代码模板

```cpp
std::string url_to_path(const std::string& url) {
    std::string path;
    if (url == "/") {
        path = "resources/index.html";  // 默认首页
    } else {
        path = "resources" + url;  // url 以 / 开头，拼出来是 resources/index.html
    }
    if (url.find("..") != std::string::npos) {
        return "";  // 路径穿越攻击，返回空表示非法
    }
    return path;
}
```

### 7.4 std::string 操作详解

#### substr

```cpp
std::string s = "hello world";
s.substr(0, 5);   // "hello"，从位置0开始，取5个字符
s.substr(6);      // "world"，从位置6开始，取到末尾
```

#### find

```cpp
std::string s = "hello world";
s.find("world");  // 返回 6（"world" 首次出现的位置）
s.find("xyz");    // 返回 std::string::npos（没找到）
s.find("o");      // 返回 4（第一个 o 的位置）
s.rfind("o");     // 返回 7（最后一个 o 的位置，从右往左找）
```

#### + 拼接

```cpp
std::string path = "resources" + url;
// url = "/index.html" → path = "resources/index.html"
```

### 7.5 常见坑

| 坑 | 现象 | 解决 |
|---|------|------|
| 没处理默认首页 `/` | 访问根目录映射到 `resources/`（目录） | 单独判断 `url == "/"` |
| 没防路径穿越 | 恶意 URL 能访问系统文件 | 检测 `..` 并拒绝 |
| `resources/` 目录不存在 | 第5步读取文件失败 | 先创建目录并放测试文件 |

cd ~/tinywebserver

# 创建 index.html

### 8.3 两个工具函数

#### get_content_type：根据后缀判断 MIME 类型

```cpp
std::string get_content_type(const std::string& path) {
    size_t dot_pos = path.rfind('.');  // 从右往左找最后一个点
    if (dot_pos == std::string::npos) return "application/octet-stream";
    std::string ext = path.substr(dot_pos + 1);  // 去掉点，比如 "html"
    if (ext == "html" || ext == "htm") return "text/html; charset=utf-8";
    if (ext == "css")  return "text/css";
    if (ext == "js")   return "application/javascript";
    if (ext == "png")  return "image/png";
    if (ext == "jpg" || ext == "jpeg") return "image/jpeg";
    if (ext == "gif")  return "image/gif";
    if (ext == "txt")  return "text/plain; charset=utf-8";
    return "application/octet-stream";
}
```

**为什么用 rfind 而不是 find？** 文件名可能有多个点（如 `style.min.css`），要取最后一个点后面的后缀。

#### read_file：读取文件内容

```cpp
bool read_file(const std::string& path, std::string& body) {
    std::ifstream file(path, std::ios::binary);  // 二进制方式打开
    if (!file.is_open()) return false;            // 文件不存在
    body.assign(std::istreambuf_iterator<char>(file),
                std::istreambuf_iterator<char>());  // 读取整个文件
    file.close();
    return true;
}
```

### 8.4 std::ifstream 详解

#### std::ios::binary 的作用

- **必须加**，否则在 Windows 上读取图片等二进制文件时，`\n` 会被转换成 `\r\n`，导致文件损坏
- 在 WSL（Linux）上默认不会转换，但加了更规范，移植性好

#### istreambuf_iterator 读取整个文件

```cpp
body.assign(std::istreambuf_iterator<char>(file),
            std::istreambuf_iterator<char>());
```

- `istreambuf_iterator<char>` 是流迭代器，逐个字节读取文件内容
- 第一个参数是文件流的起始迭代器
- 第二个参数是默认构造的结束迭代器（表示读到文件末尾）
- **这种方式能正确读取二进制文件**，包括文件中间的 `\0` 字节，因为 `std::string` 用 `size()` 记录长度，不依赖 `\0` 结束

### 8.5 二进制文件的坑（重要）

```cpp
response += body;  // ✅ 正确，std::string 的 += 用 size() 拷贝全部字节
response += body.c_str();  // ❌ 错误！c_str() 依赖 \0 结束，二进制文件中间有 \0 会被截断
```

- `body.size()`：正确的字节数，包括中间的 `\0`
- `strlen(body.c_str())`：遇到第一个 `\0` 就停止，二进制文件长度算错

### 8.6 handle_read 里的响应构造

```cpp
std::string body, content_type;
int status_code;

if (file_path.empty()) {
    status_code = 403;
    body = "<html><body><h1>403 Forbidden</h1></body></html>";
    content_type = "text/html; charset=utf-8";
} else if (!read_file(file_path, body)) {
    status_code = 404;
    body = "<html><body><h1>404 Not Found</h1></body></html>";
    content_type = "text/html; charset=utf-8";
} else {
    status_code = 200;
    content_type = get_content_type(file_path);
}

std::string response;
response += "HTTP/1.1 " + std::to_string(status_code) + " OK\r\n";
response += "Content-Length: " + std::to_string(body.size()) + "\r\n";
response += "Content-Type: " + content_type + "\r\n";
response += "Connection: close\r\n";
response += "\r\n";
response += body;  // 注意：body 可能是二进制
```

### 8.7 常见坑

| 坑 | 现象 | 解决 |
|---|------|------|
| 没加 `std::ios::binary` | 图片显示损坏 | 打开文件时加 `std::ios::binary` |
| 用 `body.c_str()` 拼响应 | 图片/二进制文件显示不全 | 直接用 `response += body` |
| Content-Length 用 `strlen` | 二进制文件长度算错 | 用 `body.size()` |
| `rfind` 写成 `find` | `style.min.css` 后缀判断错误 | 用 `rfind('.')` 找最后一个点 |
| 中文乱码 | 页面中文显示为问号 | Content-Type 加 `charset=utf-8`，文件用 UTF-8 保存 |

## 九、第6步：完善错误处理

### 9.1 目标

1. 把错误响应的构造抽成统一函数，不要到处写硬编码 HTML
2. 补全常见错误码：400/403/404/405/500
3. 支持自定义错误页面（resources/404.html 等，不存在就用默认页面）

### 9.2 HTTP 常见错误码

| 状态码 | 描述 | 触发场景 |
|--------|------|---------|
| 400 | Bad Request | 请求格式不对 |
| 403 | Forbidden | 非法路径（包含 `..`） |
| 404 | Not Found | 请求的文件不存在 |
| 405 | Method Not Allowed | 不支持的请求方法（只支持 GET） |
| 500 | Internal Server Error | 服务器内部错误 |

### 9.3 三个工具函数

#### status_to_text：状态码转描述

```cpp
std::string status_to_text(int code) {
    switch (code) {
        case 200: return "OK";
        case 400: return "Bad Request";
        case 403: return "Forbidden";
        case 404: return "Not Found";
        case 405: return "Method Not Allowed";
        case 500: return "Internal Server Error";
        default:  return "Unknown";
    }
}
```

#### make_default_error_page：构造默认错误页面

```cpp
std::string make_default_error_page(int code, const std::string& message) {
    return "<!DOCTYPE html><html><head><meta charset='utf-8'>"
           "<title>" + std::to_string(code) + " " + status_to_text(code) + "</title></head>"
           "<body style='text-align:center;padding:50px;'>"
           "<h1 style='font-size:72px;color:#666;'>" + std::to_string(code) + "</h1>"
           "<h2>" + status_to_text(code) + "</h2>"
           "<p style='color:#999;'>" + message + "</p>"
           "<hr><p><a href='/'>返回首页</a></p>"
           "</body></html>";
}
```

#### make_error_response：统一构造错误响应（核心）

```cpp
std::string make_error_response(int code, const std::string& message) {
    std::string body;
    // 优先读取自定义错误页面，比如 resources/404.html
    std::string error_page_path = "resources/" + std::to_string(code) + ".html";
    if (!read_file(error_page_path, body)) {
        body = make_default_error_page(code, message);  // 不存在就用默认页面
    }
    std::string response;
    response += "HTTP/1.1 " + std::to_string(code) + " " + status_to_text(code) + "\r\n";
    response += "Content-Length: " + std::to_string(body.size()) + "\r\n";
    response += "Content-Type: text/html; charset=utf-8\r\n";
    // ⚠️ 注意：这里不要加 Connection 头！统一在 handle_read 里加
    response += "\r\n";
    response += body;
    return response;
}
```

### 9.4 handle_read 里的错误检查顺序

```
1. 检查方法是否是 GET → 不是就 405
2. URL 映射到文件路径 → 非法就 403
3. 读取文件 → 不存在就 404
4. 全部通过 → 200，返回文件内容
```

按这个顺序检查，任何一步失败就构造对应的错误响应，跳过后面的步骤。**最后统一发送响应**（不要在每个分支里都写一遍发送逻辑）。

### 9.5 常见坑

| 坑 | 现象 | 解决 |
|---|------|------|
| 405 检查放在 URL 映射后面 | POST 请求访问不存在的文件返回 404 而不是 405 | 先检查方法，再检查 URL |
| make_error_response 里加了 Connection 头 | 错误响应有两个 Connection 头 | 统一在 handle_read 里加 |
| 发送响应的代码在 else 块里 | 405 响应构造了但没发送 | 发送代码移到 if-else 外面 |
| 自定义错误页面路径写错 | 一直显示默认页面 | 确认文件在 resources/404.html |

## 十、第7步：Keep-Alive 长连接 + 粘包处理

### 10.1 目标

1. 支持 `Connection: keep-alive`：一个 TCP 连接处理多个 HTTP 请求
2. 处理粘包：一次 recv 收到多个请求时逐个解析并返回多个响应
3. 支持 `Connection: close`：客户端要求关闭时处理完当前请求后关闭
4. HTTP/1.1 默认 keep-alive，HTTP/1.0 默认 close

### 10.2 为什么需要长连接

**短连接**：每个请求都要建连接、关连接，TCP 三次握手+四次挥手开销大。
```
客户端 → 建连接 → 发请求 → 收响应 → 关连接
客户端 → 建连接 → 发请求 → 收响应 → 关连接
```

**长连接**：一个连接处理多个请求，省去重复建连开销。浏览器加载 HTML 页面时，CSS/JS/图片等资源都可以复用同一个连接。
```
客户端 → 建连接 → 发请求1 → 收响应1 → 发请求2 → 收响应2 → ... → 关连接
```

### 10.3 reset() 函数

```cpp
void reset() {
    state_ = REQUEST_LINE;
    method_.clear();
    path_.clear();
    version_.clear();
    headers_.clear();
    content_length_ = 0;
    body_.clear();
    // ⚠️ 注意：buffer_ 不清除！里面可能还有下一个请求的粘包数据
}
```

**关键点**：`reset()` 里**不要清除 `buffer_`**。处理完一个请求后，缓冲区里可能还剩有下一个请求的数据（粘包），清除了就丢了。

### 10.4 循环解析粘包（核心）

```cpp
bool done = req->parse(buf, n);
while (done) {
    // 处理当前请求：构造响应、发送响应
    
    if (!keep_alive) {
        // 关闭连接
        close(fd);
        return;
    }
    
    // keep-alive：重置状态机，继续解析缓冲区里的下一个请求
    req->reset();
    done = req->parse("", 0);  // 用空数据触发，继续解析 buffer_ 里的剩余数据
}
```

#### parse("", 0) 的含义

`parse` 函数内部做两件事：
1. **追加阶段**：`buffer_.append(data, len)` —— 把新数据追加到缓冲区
2. **解析阶段**：`while (1) { ... }` —— 从当前状态开始解析缓冲区

传 `("", 0)` 时：
- 追加阶段：`buffer_.append("", 0)` —— 追加 0 字节，相当于什么都不做
- 解析阶段：进入 while 循环，继续解析缓冲区里剩余的数据

> 一句话：`parse("", 0)` 的意思是"我没有新数据要给你，你就把内部缓冲区里剩下的数据继续解析就行了"。

### 10.5 Connection 头的双向性（重要）

HTTP 是请求-响应协议，`Connection` 头是**双向**的：

| 方向 | 谁发的 | 作用 |
|------|--------|------|
| 请求里的 `Connection` | 客户端 → 服务器 | 客户端告诉服务器"我想保持/关闭这个连接" |
| 响应里的 `Connection` | 服务器 → 客户端 | 服务器告诉客户端"这个连接我会保持/关闭" |

**客户端是根据响应里的 `Connection` 头来决定是否复用连接的**，不是根据自己请求里发的那个。所以响应里必须加 Connection 头。

### 10.6 在响应里加 Connection 头

```cpp
size_t header_end = response.find("\r\n\r\n");
if (header_end != std::string::npos) {
    std::string conn_line = "Connection: " +
        std::string(keep_alive ? "keep-alive" : "close") + "\r\n";
    response.insert(header_end, conn_line);  // 在响应头结束前插入
}
```

- 找到响应头结束的位置（`\r\n\r\n`）
- 在它前面插入 `Connection: keep-alive` 或 `Connection: close`
- 为什么用 `insert` 而不是直接构造时加？因为 `make_error_response` 构造的响应没有 Connection 字段，统一在这里加更方便

### 10.7 keep_alive 判断规则

```cpp
bool keep_alive = true;  // 默认保持
std::string conn_header = req->getheader("Connection");
if (conn_header == "close") {
    keep_alive = false;  // 显式要求关闭
} else if (req->getversion() == "HTTP/1.0" && conn_header != "keep-alive") {
    keep_alive = false;  // HTTP/1.0 默认关闭，除非显式 keep-alive
}
// HTTP/1.1 默认 keep-alive
```

### 10.8 粘包时每个请求独立判断

`keep_alive` 变量是在 `while (done)` 循环**内部**定义的，每个请求重新判断一次。

**例子**：客户端一次发了两个请求粘在一起：
```
请求1: GET /a.html HTTP/1.1\r\nConnection: keep-alive\r\n\r\n
请求2: GET /b.html HTTP/1.1\r\nConnection: close\r\n\r\n
```

| 步骤 | 处理 | 响应里的 Connection | 结果 |
|------|------|---------------------|------|
| 1 | 解析请求1，keep-alive | `Connection: keep-alive` | 发完响应1，不关闭 |
| 2 | reset()，继续解析请求2 | - | - |
| 3 | 解析请求2，close | `Connection: close` | 发完响应2，关闭连接 |

**如果第一个请求是 close，第二个请求还会处理吗？不会。** 第一个请求要求 close，发完响应1就直接关闭连接了，缓冲区里即使还粘了第二个请求也不处理——因为连接都关了。这符合 HTTP 语义。

### 10.9 常见坑

| 坑 | 现象 | 解决 |
|---|------|------|
| `reset()` 里清除了 `buffer_` | 粘包的第二个请求丢失 | `reset()` 里不要 `buffer_.clear()` |
| `parse("", 0)` 写成 `parse(nullptr, 0)` | 崩溃 | 传空字符串 `""`，不要传 nullptr |
| 响应里没加 Connection 头 | 客户端以为要关闭，不复用连接 | 在响应头里插入 Connection 字段 |
| keep-alive 时关闭了连接 | 第二个请求发不出去 | keep-alive 时不要 close(fd)，不要 delete req |
| make_error_response 里加了 Connection 头 | 错误响应有两个 Connection 头 | 统一在 handle_read 里加 |
| Content-Length 算错 | 长连接下客户端读不到正确的响应边界，卡住 | 用 `body.size()` 精确计算 |
| 发送响应没发完就处理下一个请求 | 数据错乱 | 必须循环 send 直到全部发完 |

## 十一、踩坑记录汇总（按出现顺序）

### M1 阶段遗留

1. **`perror("lsiten")` 拼写错误** —— 应该是 `perror("listen")`
2. **send 返回值未检查** —— 非阻塞模式下 send 可能只发了一部分
3. **select 和多线程混用导致 `select: Bad file descriptor`** —— 核心错误：rfds 按值传递给线程，FD_CLR 修改的是副本；FD_ISSET 检查错了集合 rfds 而非 rset
4. **缺 `errno.h`（误写 `error.h`）** —— EAGAIN 未定义
5. **n==0 分支缺 break** —— 客户端断开后继续执行后面的代码
6. **poll 断开时 `close(-1)`** —— 先设 fd=-1 再 close，应该先保存 fd 再 close
7. **poll 新连接不找空槽位直接 max_index++** —— 数组越界
8. **epoll `close(listenfd)` 写在 while(1) 循环内** —— 处理一次事件就退出

### M3 阶段

9. **请求头 value 开头多一个空格** —— 用 `find(':')` 只找冒号，应该用 `find(": ")` 找冒号+空格，value 从 `colon + 2` 开始
10. **`make_error_response` 硬编码 `Connection: close`** —— 导致错误响应有两个 Connection 头（一个 make_error_response 里的，一个 handle_read 插入的）
11. **405 响应构造了但没发送** —— 发送响应的代码写在 else 块里，if 分支（非 GET 方法）构造了响应但跳过了发送
12. **`parse(buf + n, 0)` 越界指针** —— n==1024 时 buf+n 指向数组末尾之后，应该改成 `parse("", 0)`
13. **`reset()` 里清除 `buffer_`** —— 粘包的第二个请求丢失，reset 里不要清除 buffer_
14. **二进制文件用 `c_str()`/`strlen`** —— 图片中间有 `\0` 会被截断，应该用 `body.size()` 和 `response += body`
15. **`rfind` 写成 `find`** —— `style.min.css` 的后缀判断错误，应该用 `rfind('.')` 找最后一个点

## 十二、面试考点汇总

### HTTP 协议

1. **HTTP 请求报文由哪几部分组成？**
   - 请求行（方法+URL+版本）、请求头（键:值）、空行（\r\n）、请求体
2. **什么是粘包/半包？怎么解决？**
   - TCP 是流协议，没有消息边界。半包是一次 recv 只读了半个请求，粘包是一次 recv 读到两个请求粘在一起。解决：有限状态机，记住解析状态，累积数据，逐行解析
3. **有限状态机怎么设计？状态有哪些？**
   - 状态：REQUEST_LINE → HEADERS → BODY → FINISHED。每个连接维护缓冲区+当前状态+解析结果，每次 recv 追加数据后从当前状态继续解析
4. **GET 和 POST 的区别？**
   - GET 参数在 URL 里，POST 参数在请求体里；GET 有长度限制（URL 长度），POST 没有；GET 可缓存，POST 不可缓存；GET 幂等，POST 不幂等
5. **Keep-Alive 长连接的原理？为什么能提升性能？**
   - 一个 TCP 连接处理多个 HTTP 请求，省去重复建连（三次握手+四次挥手）的开销。浏览器加载页面时 CSS/JS/图片可复用同一连接
6. **常见 HTTP 状态码？**
   - 200 成功、301 永久重定向、302 临时重定向、400 请求错误、403 禁止访问、404 未找到、405 方法不允许、500 服务器内部错误
7. **Content-Length 的作用？**
   - 告诉客户端响应体有多少字节，客户端靠这个判断什么时候读完。长连接下必须正确，否则客户端不知道一个响应什么时候结束
8. **从输入 URL 到页面展示的完整过程？**
   - DNS 解析 → TCP 三次握手 → 发送 HTTP 请求 → 服务器解析请求 → 服务器返回响应 → 浏览器解析 HTML → 浏览器渲染页面 → （长连接）复用连接加载其他资源 → TCP 四次挥手

### C++ 语法

9. **const 成员函数的作用？**
   - 保证函数不修改类内任何成员变量。const 对象只能调用带 const 的成员函数
10. **返回成员引用的优缺点？**
    - 优点：避免拷贝，性能好；缺点：引用依赖对象生命周期，对象销毁后引用变野引用
11. **std::string 怎么处理二进制数据？**
    - std::string 用 size() 记录长度，不依赖 \0 结束，可以存储包含 \0 的二进制数据。用 .size() 而不是 strlen()，用 += 而不是 += c_str()
12. **ifstream 读取二进制文件为什么要加 ios::binary？**
    - 不加的话，Windows 上 \n 会被转换成 \r\n，导致文件损坏。Linux 上默认不转换，但加了更规范

14. **Reactor 模型的原理？**（M2 内容）
15. **单 Reactor 单线程 vs 单 Reactor 多线程？**（M2+M4 内容）

## 十三、HTTP vs HTTPS（补充，面试常问）

> HTTPS = **HTTP + SSL/TLS**

### 核心对比

| 对比项 | HTTP | HTTPS |
|--------|------|-------|
| 端口 | 80 | 443 |
| 安全性 | 明文传输，可窃听篡改 | 加密传输，防窃听防篡改 |
| 证书 | 不需要 | 需要 CA 颁发的数字证书 |
| 性能 | 无额外开销 | 多 TLS 握手+加解密 CPU 开销 |
| 协议层级 | 应用层，直接跑在 TCP 上 | HTTP → TLS 层 → TCP 层 |

### 简单流程对比

- HTTP：TCP 三次握手 → 直接发送 HTTP 请求报文
- HTTPS：TCP 三次握手 → **TLS 握手（协商加密算法、交换密钥、校验证书）** → 加密后的 HTTP 报文传输

### 面试一句话背诵

> HTTP 是明文的应用层协议，默认 80 端口，传输数据可以被抓包篡改；HTTPS 是在 HTTP 和 TCP 中间增加 TLS 安全层，默认 443 端口，依靠数字证书做身份认证，报文加密传输，代价是多了 TLS 握手和加解密的 CPU 开销。
