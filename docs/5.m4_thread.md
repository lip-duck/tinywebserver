# M4 线程池 —— 完整学习笔记

> 对应零声课程 3.1.1，TinyWebServer 的线程池模块。
> 目标：实现 C++11 线程池，把业务处理从主线程移到工作线程，构成"单 Reactor + 线程池"模型。

---

## 一、M4 概述

### 1.1 为什么需要线程池？

M3 是**单 Reactor 单线程**模型：主线程既要做 `epoll_wait` 事件分发，又要做业务处理（读文件、构造响应）。

**问题**：如果业务处理很慢（读大文件、查数据库），主线程被卡住，`epoll_wait` 不能及时返回，其他连接的事件处理不了，整个服务器卡顿。

**解决**：主线程只负责 IO 事件分发（accept、recv），业务处理（读文件、构造响应、send）丢给**线程池**里的工作线程执行。

```
主线程（Reactor）                    工作线程（线程池）
┌─────────────────────┐            ┌──────────────────────┐
│ epoll_wait           │            │ 读文件（慢操作）      │
│ accept 新连接        │            │ 构造 HTTP 响应        │
│ recv 数据            │ ──submit──>│ 循环 send 响应        │
│ 解析 HTTP（状态机）  │            │ 关闭连接（close 时）  │
│ 提交任务给线程池     │            └──────────────────────┘
└─────────────────────┘
```

### 1.2 五步路线

| 步骤 | 目标 | 核心知识点 |
|------|------|-----------|
| 1 | C++11 线程基础 | std::thread、join/detach、std::mutex、std::lock_guard |
| 2 | 条件变量 | std::condition_variable、wait/notify、虚假唤醒、生产者-消费者 |
| 3 | 任务队列 | std::queue + std::function + 互斥锁 + 条件变量 |
| 4 | 线程池类 | 固定线程数、submit 提交任务、stop 优雅退出、RAII |
| 5 | 集成到 WebServer | 主线程做 IO，业务处理丢给线程池，短连接模式 |

## 二、第一步：C++11 线程基础

### 2.1 std::thread 创建线程

```cpp
#include <thread>

void worker(int id) {
    std::cout << "线程 " << id << " 开始工作" << std::endl;
}

int main() {
    std::thread t1(worker, 1);  // 创建线程，执行 worker(1)
    std::thread t2(worker, 2);
    t1.join();  // 主线程等待 t1 结束
    t2.join();
    return 0;
}
```

**语法要点**：
- `std::thread t(函数名, 参数1, 参数2, ...)` —— 创建线程并立即开始执行
- 参数可以是任意类型，内部会拷贝一份传给线程函数
- 线程函数可以是：普通函数、lambda、成员函数（需传对象指针）、仿函数

**std::thread 构造函数原型**：
```cpp
template<class Function, class... Args>
explicit thread(Function&& f, Args&&... args);
```
- `f`：可调用对象
- `args...`：传给 f 的参数（可变参数）
- **构造时立即启动线程**，不需要额外调用 start()

### 2.2 join vs detach

| 方式 | 作用 | 特点 |
|------|------|------|
| `t.join()` | 主线程**阻塞等待**子线程结束 | 安全，能拿到执行结果 |
| `t.detach()` | 子线程**分离**，主线程不等 | 后台运行，不能再 join |

> ⚠️ **必须二选一**：一个 std::thread 对象要么 join，要么 detach，什么都不做就析构会调用 `std::terminate` 崩溃。

### 2.3 数据竞争与 std::mutex

多个线程同时修改同一个变量会出问题：

```cpp
int counter = 0;
void increment() {
    for (int i = 0; i < 100000; i++) {
        counter++;  // ❌ 多个线程同时改，结果不确定
    }
}
```

**解决：互斥锁 std::mutex**

```cpp
#include <mutex>
std::mutex mtx;
void increment() {
    for (int i = 0; i < 100000; i++) {
        mtx.lock();
        counter++;
        mtx.unlock();
    }
}
```

### 2.4 std::lock_guard（RAII 锁，推荐）

手动 lock/unlock 容易忘记 unlock（中间 return 了）。用 `std::lock_guard` 自动管理：

```cpp
void increment() {
    for (int i = 0; i < 100000; i++) {
        std::lock_guard<std::mutex> lock(mtx);  // 构造时加锁
        counter++;
    }  // 作用域结束，lock 析构自动解锁
}
```

**原理**：RAII（资源获取即初始化），构造函数加锁，析构函数解锁。

**lock_guard 核心特性**：
1. 不可拷贝、不可移动
2. 构造即上锁，没有延迟上锁选项（和 unique_lock 最大区别）
3. 作用域 = 锁生命周期，大括号就是锁边界

### 2.5 emplace_back 创建线程（重点语法）

```cpp
std::vector<std::thread> threads;
threads.emplace_back(increment);
```

**逐层拆解**：

1. **`emplace_back(args...)`**：在 vector 末尾**直接构造**元素，把参数转发给元素的构造函数。等价于（但更高效）：
   ```cpp
   threads.push_back(std::thread(increment));
   ```
   - `push_back`：先构造临时 thread 对象 → 再移动进 vector
   - `emplace_back`：**直接在 vector 内存上构造** thread，零额外开销

2. **`increment` 不需要加括号**：
   ```cpp
   threads.emplace_back(increment);   // ✅ 传函数指针（函数名自动退化为指针）
   threads.emplace_back(increment()); // ❌ 先调用 increment()，把返回值传给 thread 构造
   ```
   `increment` 是函数名，作为参数时自动退化为函数指针，std::thread 拿到这个地址在线程里调用。

3. **完整执行流程**（循环 4 次）：
   - i=0：构造第 1 个 thread，启动线程执行 increment()
   - i=1：构造第 2 个 thread，启动线程执行 increment()
   - ...
   - 循环结束后，4 个线程同时在跑，各自对 counter 加 100000 次

### 2.6 编译注意

Linux 下用 std::thread 必须加 `-pthread` 编译选项，否则链接报错：
```bash
g++ -o m4_step1 m4_step1.cpp -std=c++11 -pthread
```

## 三、第二步：条件变量（std::condition_variable）

### 3.1 为什么需要条件变量？

mutex 只能解决"互斥访问"，不能解决"等待某个条件成立"。

**场景**：生产者往队列放任务，消费者从队列取任务。队列空时消费者怎么办？

| 方案 | 问题 |
|------|------|
| `while(queue.empty()) {}` 轮询 | **忙等**，CPU 占用 100% |
| `sleep(1)` 然后检查 | 响应延迟，任务来了最多等 1 秒 |
| **条件变量** | 队列空时消费者**阻塞睡眠**，任务来了生产者**唤醒**，零 CPU 占用，立即响应 |

### 3.2 std::condition_variable 详解

```cpp
#include <condition_variable>
std::condition_variable cv;
std::mutex mtx;
```

**三个核心操作**：

| 操作 | 函数 | 作用 |
|------|------|------|
| 等待 | `cv.wait(lock, predicate)` | 阻塞当前线程，直到被通知且条件成立 |
| 通知一个 | `cv.notify_one()` | 唤醒一个正在等待的线程 |
| 通知全部 | `cv.notify_all()` | 唤醒所有正在等待的线程 |

### 3.3 wait 内部做了什么（关键！）

```cpp
cv.wait(lock, predicate);
```

1. **自动释放锁**：wait 内部调用 `lock.unlock()`，让其他线程能拿到锁
2. **阻塞睡眠**：当前线程进入睡眠，等待 notify
3. **被唤醒后自动重新加锁**：收到 notify 后，wait 内部调用 `lock.lock()`
4. **检查谓词**：条件成立则 wait 返回；不成立则回到第 1 步继续等

> 这就是为什么 wait 必须用 `unique_lock`（不是 lock_guard）：wait 内部需要自动解锁和重新加锁，lock_guard 不支持手动解锁。

### 3.4 虚假唤醒（spurious wakeup）

**什么是虚假唤醒**：线程没有收到 notify，却莫名其妙从 wait 中醒来了。是操作系统底层特性，不是 bug。

**怎么解决**：醒来后**重新检查条件**，不成立就继续等。这就是必须用 `while` 而不是 `if` 的原因。

```cpp
// ❌ 错误：用 if，虚假唤醒后条件不成立也继续执行
if (queue.empty()) { cv.wait(lock); }

// ✅ 正确：用 while，醒来后重新检查
while (queue.empty()) { cv.wait(lock); }

// ✅ 带谓词的 wait（推荐，内部就是 while 循环）
cv.wait(lock, []() { return !queue.empty(); });
```

### 3.5 unique_lock vs lock_guard

| 对比项 | std::lock_guard | std::unique_lock |
|--------|----------------|-----------------|
| 自动加锁解锁 | ✅ | ✅ |
| 手动解锁/加锁 | ❌ 不支持 | ✅ `lock.unlock()` / `lock.lock()` |
| 可移动 | ❌ 不可移动 | ✅ 支持 move |
| 性能 | 略高 | 略低 |
| 适用场景 | 简单互斥 | 条件变量（必须用 unique_lock） |

### 3.6 生产者-消费者模型（经典模板）

```cpp
std::queue<int> task_queue;
std::mutex mtx;
std::condition_variable cv;
bool finished = false;

// 生产者
void producer() {
    for (int i = 1; i <= 10; i++) {
        {
            std::lock_guard<std::mutex> lock(mtx);
            task_queue.push(i);
        }
        cv.notify_one();  // 解锁后再通知
    }
    {
        std::lock_guard<std::mutex> lock(mtx);
        finished = true;
    }
    cv.notify_all();
}

// 消费者
void consumer(int id) {
    while (true) {
        std::unique_lock<std::mutex> lock(mtx);
        cv.wait(lock, []() { return !task_queue.empty() || finished; });

        if (!task_queue.empty()) {
            int task = task_queue.front();
            task_queue.pop();
            lock.unlock();  // 取到任务后解锁，执行任务时不占锁
            // 执行 task...
        } else if (finished) {
            break;  // 队列空且生产者结束，退出
        }
    }
}
```

**关键要点**：
1. **notify 放在锁外面**：如果在锁内 notify，被唤醒的消费者立即尝试加锁但锁还在生产者手里，多一次无效加锁尝试
2. **取到任务后 unlock**：执行任务可能耗时，一直占锁会导致其他线程无法操作队列，并发度降为 0
3. **谓词用 `!empty() || finished`**：有任务就干活，收到结束指令就退出

### 3.7 常见坑

| 坑 | 现象 | 解决 |
|---|------|------|
| wait 用 lock_guard 而不是 unique_lock | 编译报错 | 条件变量必须用 unique_lock |
| 用 if 而不是 while 检查条件 | 虚假唤醒后条件不成立也继续执行 | 用 while 或带谓词的 wait |
| notify 放在锁内 | 性能略低（被唤醒线程抢不到锁） | 解锁后再 notify |
| 取到任务后不 unlock | 执行任务时长时间占锁，并发度为 0 | 取到任务后 lock.unlock() |
| 忘记 notify | 消费者永远阻塞 | 每次放任务后 notify_one()，结束时 notify_all() |
| finished 标志没保护 | 数据竞争 | 读写 finished 都要加锁 |

## 四、第三步：任务队列（std::function + 封装类）

### 4.1 为什么需要 std::function？

第二步的任务队列是 `std::queue<int>`，只能存整数。但线程池里的任务是各种各样的（读文件、查数据库、写日志），需要一个能"装下任意可调用对象"的类型——`std::function<void()>`。

### 4.2 std::function 详解

```cpp
#include <functional>
std::function<void()> task;  // 能包装"无参数、无返回值"的任意可调用对象
```

**能包装什么**：
```cpp
// 1. 普通函数
void foo() { ... }
task = foo;

// 2. lambda（最常用）
task = []() { ... };

// 3. 带捕获的 lambda
int x = 42;
task = [x]() { std::cout << x; };

// 4. 仿函数（重载了 operator() 的类对象）
struct MyFunc { void operator()() { ... } };
task = MyFunc();

// 5. std::bind 表达式
task = std::bind(foo);
```

**执行**：`task();` —— 像普通函数一样调用。

**带参数和返回值**：
```cpp
std::function<int(int, int)> add = [](int a, int b) { return a + b; };
int result = add(3, 4);  // 7
```
模板参数是 `返回值类型(参数类型列表)`。线程池里统一用 `void()`。

**本质**：
- 是一个类，内部用**类型擦除**（type erasure）技术包装任意可调用对象
- 有**小对象优化**（SSO）：小 lambda 直接存在对象内部，大的才堆分配
- 空的 std::function 调用会抛 `std::bad_function_call` 异常

### 4.3 std::ref（重点语法）

**作用**：包装一个变量，生成引用包装器 `std::reference_wrapper<T>`，解决模板传参时**值拷贝**的问题。

**最常用场景：向 std::thread 传引用参数**

```cpp
void worker(std::queue<int>& task_queue) { ... }

int main() {
    std::queue<int> tq;
    // ❌ 错误：thread 会拷贝一份 tq，子线程操作的是副本
    // std::thread th(worker, tq);

    // ✅ 正确：std::ref 包装，传递引用，子线程操作原始 tq
    std::thread th(worker, std::ref(tq));
}
```

> ⚠️ 含 `std::mutex` / `std::condition_variable` 的对象**不可拷贝**，直接传给 thread 会编译报错，必须用 `std::ref` 或指针。

**和裸引用、指针对比**：

| 写法 | 本质 | 适用 |
|------|------|------|
| `std::ref(x)` | reference_wrapper，可传给模板/thread | 推荐，可读性好 |
| `&x` | 裸指针 | 也能用，但函数参数要改成指针类型 |
| 直接传 x | 值拷贝，新建副本 | 多线程场景不想要 |

> `std::ref` 主要用于向 std::thread、std::bind 这类模板函数传参。lambda 捕获 `[&]` 不需要 std::ref。

### 4.4 任务队列类设计

把生产者-消费者模型封装成类，对外暴露三个接口：

| 接口 | 作用 |
|------|------|
| `push(task)` | 生产者：放任务进队列，通知消费者 |
| `pop(task)` | 消费者：取任务，队列空就阻塞等待 |
| `stop()` | 停止队列，唤醒所有消费者退出 |

### 4.5 TaskQueue 完整代码

```cpp
class TaskQueue {
public:
    TaskQueue() : stop_(false) {}

    void push(std::function<void()> task) {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            queue_.push(std::move(task));  // 移动，避免拷贝
        }
        cv_.notify_one();
    }

    bool pop(std::function<void()>& task) {
        std::unique_lock<std::mutex> lock(mutex_);
        cv_.wait(lock, [this]() { return !queue_.empty() || stop_; });
        if (queue_.empty()) return false;  // 停止且空
        task = std::move(queue_.front());
        queue_.pop();
        return true;
    }

    void stop() {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            stop_ = true;
        }
        cv_.notify_all();
    }

private:
    std::queue<std::function<void()>> queue_;
    std::mutex mutex_;
    std::condition_variable cv_;
    bool stop_;
};
```

**关键要点**：
- `pop` 返回值用 `bool`，task 用**引用参数**输出（比返回 std::function 更高效，避免移动）
- `std::move(task)` 移动进队列，避免拷贝 lambda（大 lambda 拷贝有开销）
- `stop_` 设置必须在锁内，防止和消费者的 wait 谓词检查竞争

### 4.6 常见坑

| 坑 | 现象 | 解决 |
|---|------|------|
| TaskQueue 含 mutex，直接传给线程 | 编译报错（mutex 不可拷贝） | 用 std::ref(tq) 或传指针 |
| push 时不用 std::move | lambda 大时有拷贝开销 | queue_.push(std::move(task)) |
| stop 后不 notify_all | 消费者永远阻塞 | stop 时 cv_.notify_all() |
| lambda 捕获循环变量引用 [&i] | 所有任务打印同一个 i（最后一个值） | 按值捕获 [i] 或 [task_id] |
| 空的 std::function 被调用 | 抛 std::bad_function_call | pop 返回 true 时 task 一定非空 |

## 五、第四步：线程池类（ThreadPool）

### 5.1 设计目标

把 TaskQueue 和工作线程封装成完整的线程池类，对外只暴露：

```cpp
ThreadPool pool(4);           // 创建 4 个工作线程
pool.submit([](){ ... });     // 提交任务，自动分配线程执行
// 程序结束时 pool 析构自动停止所有线程
```

### 5.2 类结构

```
ThreadPool
├── 内部成员
│   ├── queue<std::function<void()>> tasks_   任务队列
│   ├── vector<thread> workers_                工作线程数组
│   ├── mutex mutex_                           保护队列和 stop_
│   ├── condition_variable cv_                 条件变量
│   └── bool stop_                             停止标志
├── 对外接口
│   ├── ThreadPool(int num)       构造：创建 num 个工作线程
│   ├── submit(task)              提交任务
│   ├── stop()                    停止所有线程，join 等待
│   └── ~ThreadPool()             析构：自动调用 stop()
└── 内部函数
    └── worker()                  工作线程主循环
```

### 5.3 ThreadPool 完整代码

```cpp
class ThreadPool {
public:
    explicit ThreadPool(int num_threads) : stop_(false) {
        for (int i = 0; i < num_threads; i++) {
            workers_.emplace_back([this]() {
                this->worker();
            });
        }
    }

    void submit(std::function<void()> task) {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            if (stop_) {
                std::cerr << "线程池已停止，拒绝提交任务" << std::endl;
                return;
            }
            tasks_.push(std::move(task));
        }
        cv_.notify_one();
    }

    void stop() {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            if (stop_) return;  // 防止重复调用
            stop_ = true;
        }
        cv_.notify_all();
        for (auto& t : workers_) {
            if (t.joinable()) t.join();
        }
    }

    ~ThreadPool() { stop(); }

    // 禁止拷贝和移动
    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;

private:
    void worker() {
        std::function<void()> task;
        while (true) {
            {
                std::unique_lock<std::mutex> lock(mutex_);
                cv_.wait(lock, [this]() {
                    return !tasks_.empty() || stop_;
                });
                if (stop_ && tasks_.empty()) {
                    return;  // 停止且队列空，退出
                }
                task = std::move(tasks_.front());
                tasks_.pop();
            }  // 解锁：执行任务时不占锁
            task();  // 执行任务（在锁外）
        }
    }

    std::queue<std::function<void()>> tasks_;
    std::vector<std::thread> workers_;
    std::mutex mutex_;
    std::condition_variable cv_;
    bool stop_;
};
```

### 5.4 逐行讲解关键部分

#### 构造函数：创建工作线程

```cpp
explicit ThreadPool(int num_threads) : stop_(false) {
    for (int i = 0; i < num_threads; i++) {
        workers_.emplace_back([this]() {
            this->worker();
        });
    }
}
```

- `explicit`：防止隐式类型转换，`ThreadPool pool = 4;` 会编译报错
- `[this]() { this->worker(); }`：lambda 捕获 this 指针，调用成员函数 worker()
- 构造函数结束时，所有工作线程已经启动，在 worker() 里阻塞等待任务

#### worker：工作线程主循环（最容易写错的地方）

```cpp
void worker() {
    std::function<void()> task;
    while (true) {
        {  // 大括号开始：限制 lock 的作用域
            std::unique_lock<std::mutex> lock(mutex_);
            cv_.wait(lock, [this]() { return !tasks_.empty() || stop_; });
            if (stop_ && tasks_.empty()) return;
            task = std::move(tasks_.front());
            tasks_.pop();
        }  // 大括号结束：lock 析构，自动解锁
        task();  // 在循环内、锁外执行任务
    }
}
```

**三个关键点**：
1. **`task()` 必须在 while 循环里面**：不能写在 while 外面（while 是死循环，永远走不到外面）
2. **用大括号 `{}` 限制 lock 作用域**：取到任务后出作用域自动解锁
3. **在锁外执行 `task()`**：任务可能耗时，占着锁会导致其他线程无法取任务，并发度降为 0

#### stop：优雅退出

```cpp
void stop() {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        if (stop_) return;  // 防止重复调用
        stop_ = true;
    }
    cv_.notify_all();
    for (auto& t : workers_) {
        if (t.joinable()) t.join();
    }
}
```

- `if (stop_) return`：防止重复调用（析构函数也会调用 stop）
- worker 退出条件是 `stop_ && tasks_.empty()`：停止了但队列还有任务时，继续执行完队列里的任务再退出（**优雅退出**）
- `t.joinable()` 检查：线程已经 join 过或 detach 过就不能再 join

#### 析构函数（RAII）

```cpp
~ThreadPool() { stop(); }
```

RAII 思想：对象销毁时自动停止线程池，不需要手动调用 stop()。

#### 禁止拷贝

```cpp
ThreadPool(const ThreadPool&) = delete;
ThreadPool& operator=(const ThreadPool&) = delete;
```

含 std::mutex 和 std::thread 的对象不可拷贝，用 `= delete` 显式删除。

### 5.5 std::atomic 原子计数器

```cpp
#include <atomic>
std::atomic<int> counter(0);
counter++;  // 原子操作，多线程同时 ++ 也不会出错
```

- `std::atomic<int>` 是原子类型，`++` 操作是原子的，多线程同时自增不会有数据竞争
- 不需要 mutex 保护，比 mutex 轻量
- 线程池里统计任务数、连接数等简单计数都用 std::atomic

### 5.6 单例模式（TinyWebServer 中的用法）

```cpp
class ThreadPool {
public:
    static ThreadPool* get_instance(int num_threads = 4) {
        static ThreadPool instance(num_threads);  // C++11 局部静态变量线程安全
        return &instance;
    }
private:
    explicit ThreadPool(int num_threads) : stop_(false) { ... }
    ~ThreadPool() { stop(); }
    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;
};
```

C++11 保证局部静态变量的初始化是线程安全的（多个线程同时调用 get_instance，只有一个线程执行初始化）。

### 5.7 常见坑

| 坑 | 现象 | 解决 |
|---|------|------|
| task() 写在 while 循环外面 | 任务永远不执行，counter 永远是 0 | task() 必须在 while 循环里面 |
| 取到任务后不解锁 | 执行任务时占着锁，并发度降为 0 | 用大括号限制 lock 作用域，锁外执行 task() |
| 析构时忘记 stop | 工作线程还在跑，主程序退出崩溃 | 析构函数调用 stop() |
| stop 重复调用 | join 已 join 的线程崩溃 | if (stop_) return 防重复 |
| stop 后还能 submit | 任务提交了但永远不执行 | submit 里检查 stop_ |
| 工作线程 lambda 没捕获 this | 编译报错或访问非法内存 | [this]() { worker(); } |
| join 前没检查 joinable | 线程已 detach 或 join，再 join 崩溃 | if (t.joinable()) t.join(); |
| 用普通 int 做计数器 | 多线程 ++ 数据竞争 | 用 std::atomic<int> |

## 六、第五步：集成到 WebServer

### 6.1 集成架构

```
主线程（eventloop）                    工作线程（线程池）
┌─────────────────────┐              ┌──────────────────────┐
│ epoll_wait           │              │ 读文件（慢操作）      │
│ accept 新连接        │              │ 构造 HTTP 响应        │
│ recv 数据            │ ──submit──> │ 循环 send 响应        │
│ 解析 HTTP（状态机）  │              │ 关闭连接（close 时）  │
│ 提交任务给线程池     │              └──────────────────────┘
└─────────────────────┘
```

**核心原则**：
- 主线程只做 **IO**（accept/recv）和 **解析**（操作 HttpRequest，per-connection 无竞争）
- 工作线程做 **慢操作**（读文件、构造响应、send）
- 解析完成后才提交任务，避免工作线程和主线程同时操作 req

### 6.2 需要做的修改

1. 把 ThreadPool 类加到 m3_http.cpp 里
2. 新增全局变量 `ThreadPool* g_pool = nullptr;`
3. 把 handle_read 里的业务处理抽成 `process_request` 函数
4. handle_read 里解析完成后 `g_pool->submit(...)` 提交任务
5. main 里创建和销毁线程池

### 6.3 为什么要把业务处理抽成 process_request？

1. **线程池 submit 需要一个可调用对象**：业务处理嵌在 handle_read 的 while 循环里，不是独立的可调用对象，没法直接 submit
2. **主线程和工作线程的代码必须物理分离**：handle_read 在主线程执行，process_request 在工作线程执行。不抽出来就分不清哪些代码在哪个线程跑，也没法做线程安全分析
3. **职责单一 + 可复用**

### 6.4 M4 阶段推荐：短连接模式

集成线程池后，如果保持 keep-alive，会有复杂的线程安全问题（工作线程 reset req 的同时主线程可能 recv 新数据并 parse）。M4 阶段推荐**短连接模式**：

**修改 handle_read：解析完成后从 epoll 移除 fd，再提交任务**

```cpp
bool done = req->parse(buf, n);
if (done) {
    // 【关键】从 epoll 移除 fd，防止工作线程处理期间主线程又收到新数据
    g_loop->deletechannel(ch);
    // 提交任务给线程池
    g_pool->submit([fd, req, ch]() {
        process_request(fd, req, ch);
    });
    break;  // 跳出 recv 循环
}
```

**修改 process_request：工作线程不操作 eventloop，直接清理**

```cpp
void process_request(int fd, Httprequest* req, channel* ch) {
    // ... 构造响应、循环 send（和原来一样）...

    // 【关键】工作线程不操作 g_loop（已经在主线程里 deletechannel 了）
    // 直接 close + 清理
    close(fd);
    delete ch;
    delete req;
    g_http_requests.erase(fd);

    // 所有响应强制 Connection: close（短连接模式）
}
```

**这样修改后的效果**：

| 问题 | 解决方式 |
|------|---------|
| 同一个 fd 多个任务并发处理 | 提交任务前从 epoll 移除 fd，主线程不会再收到这个 fd 的事件 |
| 工作线程操作 eventloop | 工作线程不调用 deletechannel，只 close(fd) |
| keep-alive 数据竞争 | 暂时不支持 keep-alive，所有连接短连接 |
| 粘包第二个请求 | 短连接模式下丢弃（连接要 close 了），M5 再完善 |

#### ⚠️ 必须强制 close 的实际坑（浏览器 keep-alive 转圈）

如果 `process_request` 里的 `keep_alive` 判断还是原来的逻辑（根据请求头判断，不是强制 close），会出现**浏览器一直转圈、服务器看起来像阻塞了**的问题：

```
浏览器发请求：HTTP/1.1 + Connection: keep-alive
    ↓
process_request 里 keep_alive 判断：HTTP/1.1 + keep-alive → keep_alive = true
    ↓
工作线程发完响应后，keep_alive=true 分支：req->reset()，不 close(fd)，不 delete
    ↓
但 fd 已经在 handle_read 里从 epoll 移除了（deletechannel）
    ↓
浏览器以为是 keep-alive，等着发下一个请求或等服务器关连接
    ↓
服务器永远不会再处理这个 fd 的事件了（已从 epoll 移除）
    ↓
浏览器一直转圈，服务器终端没有新输出 → 看起来像"阻塞住了"
```

**解决方案**：M4 短连接模式下，`process_request` 里必须**强制 `keep_alive = false`**，或者**无条件 `close(fd)`**，不能保留原来的 keep_alive 判断逻辑。同时响应头里必须加 `Connection: close`，告诉浏览器这个连接用完就关。

```cpp
void process_request(int fd, Httprequest* req, channel* ch) {
    // 【关键】M4 阶段强制短连接，不支持 keep-alive
    bool keep_alive = false;

    // ... 构造响应（响应头里加 Connection: close）...

    // 【关键】无条件关闭连接，不要用 if(keep_alive) 分支
    close(fd);
    delete ch;
    delete req;
    g_http_requests.erase(fd);
}
```

### 6.5 为什么 M4 阶段暂时不支持 keep-alive？

keep-alive 需要工作线程处理完后**重新把 fd 加回 epoll**，但工作线程不能操作 eventloop（不是线程安全的）。需要 runInLoop 机制把"重新注册读事件"丢回主线程执行，这是 M5/M6 的内容。M4 阶段重点是理解线程池集成，短连接模式足够。

### 6.6 线程安全注意事项（M4 阶段已知问题）

| 问题 | 风险 | M4 处理 | 后续完善 |
|------|------|---------|---------|
| 工作线程操作 g_http_requests | 多线程同时 erase/insert 数据竞争 | 短连接模式下每个 fd 只被一个工作线程操作，概率低 | M5 加 mutex 保护 |
| 工作线程 close(fd) 但 channel 还在 epoll 里 | epoll 检查已关闭 fd | 提交任务前主线程已 deletechannel | 正常流程 |
| 工作线程 send 时主线程同时 send | 同一个 fd 被两个线程写 | 提交任务前已从 epoll 移除，主线程不会再 send | 正常流程 |

### 6.7 常见坑

| 坑 | 现象 | 解决 |
|---|------|------|
| 工作线程里调用 g_loop->deletechannel | 崩溃或数据竞争（eventloop 不是线程安全的） | 工作线程不要操作 eventloop，只 close(fd) |
| 提交任务后没有从 epoll 移除 fd | 工作线程处理期间主线程又收到新数据，同一个 fd 多个任务并发，send 顺序混乱 | 提交任务前 g_loop->deletechannel(ch) |
| 提交任务后没有 break | 主线程继续 recv，可能又解析完一个请求提交第二个任务 | 提交任务后 break 跳出 recv 循环 |
| 忘记创建 g_pool | 空指针崩溃 | main 里 g_pool = new ThreadPool(4) |
| 编译忘记加 -pthread | 链接报错 | g++ ... -pthread |
| 粘包第二个请求不处理 | 客户端发两个请求粘在一起，只处理第一个 | M4 短连接模式下可接受，M5 完善 keep-alive 时再处理 |
| 🔴 keep_alive 判断没改成强制 close | 浏览器发 keep-alive 请求，工作线程不 close(fd)，fd 已从 epoll 移除，浏览器一直转圈，服务器看起来像阻塞了 | process_request 里强制 keep_alive=false，或无条件 close(fd)，响应头加 Connection: close |

## 七、踩坑记录汇总（按出现顺序）

### 语法/基础类

1. **编译忘记加 -pthread** —— Linux 下用 std::thread 必须加 `-pthread`，否则链接报错
2. **std::thread 对象既不 join 也不 detach** —— 析构时调用 std::terminate 崩溃，必须二选一
3. **向 std::thread 传引用参数忘记 std::ref** —— thread 会拷贝对象，含 mutex 的对象不可拷贝，编译报错。必须用 std::ref(tq)
4. **lambda 捕获循环变量引用 [&i]** —— 所有任务打印同一个 i（最后一个值）。必须按值捕获 [i] 或 [task_id]
5. **函数名传给 thread 时加了括号** —— `emplace_back(increment())` 会先调用 increment() 把返回值传给 thread 构造。应该传函数名 `increment`（自动退化为函数指针）

### 条件变量类

6. **wait 用 lock_guard 而不是 unique_lock** —— 编译报错。条件变量必须用 unique_lock（wait 内部要自动解锁和重新加锁）
7. **用 if 而不是 while 检查条件** —— 虚假唤醒后条件不成立也继续执行，可能崩溃。必须用 while 或带谓词的 wait
8. **notify 放在锁内** —— 被唤醒的线程立即尝试加锁但锁还在通知者手里，多一次无效加锁尝试。应该解锁后再 notify
9. **取到任务后不 unlock** —— 执行任务时长时间占锁，其他线程无法取任务，并发度降为 0。取到任务后必须 lock.unlock()
10. **忘记 notify** —— 消费者永远阻塞。每次放任务后 notify_one()，结束时 notify_all()
11. **finished/stop_ 标志没在锁内设置** —— 数据竞争。设置标志必须加锁

### 线程池类

12. **🔴 task() 写在 while(1) 循环外面** —— 任务永远不执行。while(1) 是死循环，只有 return 能退出，但 return 直接退出整个函数，task() 根本执行不到。必须写在 while 循环里面
13. **🔴 取到任务后锁没有释放** —— unique_lock 作用域是整个 while 循环体，执行 task() 时还占着锁，并发度降为 0。必须用大括号 {} 限制 lock 作用域，锁外执行 task()
14. **析构时忘记 stop** —— 工作线程还在跑，主程序退出崩溃。析构函数必须调用 stop()
15. **stop 重复调用** —— join 已 join 的线程崩溃。if (stop_) return 防重复
16. **stop 后还能 submit** —— 任务提交了但永远不执行。submit 里检查 stop_，已停止则拒绝
17. **工作线程 lambda 没捕获 this** —— 编译报错或访问非法内存。必须 [this]() { worker(); }
18. **join 前没检查 joinable** —— 线程已 detach 或 join，再 join 崩溃。if (t.joinable()) t.join()
19. **用普通 int 做计数器** —— 多线程 ++ 数据竞争，结果不对。用 std::atomic<int>
20. **线程池对象被拷贝** —— 编译报错（mutex 不可拷贝）。用 = delete 删除拷贝构造

### 集成到 WebServer

21. **🔴 提交任务后没有从 epoll 移除 fd** —— 工作线程处理期间主线程又收到新数据，同一个 fd 多个任务并发处理，send 响应顺序混乱。提交任务前必须 g_loop->deletechannel(ch)
22. **🔴 工作线程操作 g_loop->deletechannel** —— eventloop 不是线程安全的，工作线程操作 epoll 会数据竞争甚至崩溃。工作线程不要操作 eventloop，只 close(fd)
23. **提交任务后没有 break** —— 主线程继续 recv 循环，可能又解析完一个请求提交第二个任务。提交任务后必须 break
24. **keep-alive 时工作线程 reset req，主线程同时 recv parse** —— req 状态被两个线程同时修改，数据竞争。M4 阶段暂时用短连接模式，M5 完善
25. **粘包第二个请求不处理** —— handle_read 里 if(done) 而不是 while(done)，只处理第一个请求。M4 短连接模式下可接受，M5 完善
26. **🔴 keep_alive 判断没改成强制 close，浏览器一直转圈** —— 浏览器发 HTTP/1.1 + Connection: keep-alive 请求，process_request 里 keep_alive 判断还是原来的逻辑（不是强制 close），导致 keep_alive=true，工作线程发完响应后不 close(fd)，连接保持。但 fd 已经从 epoll 移除了，浏览器的下一个请求永远不会被处理，浏览器一直转圈，服务器终端没有新输出，看起来像"阻塞住了"。解决方案：M4 短连接模式下 process_request 里必须强制 keep_alive=false，或无条件 close(fd)，响应头里加 Connection: close

## 八、面试考点汇总

### 线程基础

1. **std::thread 和 pthread 的区别？**
   - std::thread 是 C++11 标准库，跨平台，RAII 风格，支持 lambda/函数对象
   - pthread 是 POSIX 标准，C 风格，只在类 Unix 系统，功能更底层
   - std::thread 底层在 Linux 上就是封装 pthread

2. **join 和 detach 的区别？**
   - join：主线程阻塞等待子线程结束，安全，能拿到结果
   - detach：子线程分离，主线程不等，后台运行，不能再 join
   - 必须二选一，否则析构时 std::terminate 崩溃

3. **什么是数据竞争？怎么解决？**
   - 多个线程同时读写同一个共享变量，结果不确定
   - 解决：互斥锁 std::mutex、原子操作 std::atomic、线程局部存储 thread_local

4. **lock_guard 和 unique_lock 的区别？**
   - lock_guard：简单，构造即上锁，不可手动解锁，不可移动，性能略高
   - unique_lock：灵活，支持手动解锁/加锁，可移动，条件变量必须用它
   - 简单互斥用 lock_guard，条件变量用 unique_lock

### 条件变量

5. **条件变量的作用？wait 内部做了什么？**
   - 作用：实现"等待-通知"机制，避免忙等
   - wait 内部：自动解锁 → 阻塞睡眠 → 被唤醒后自动加锁 → 检查谓词
   - 必须用 unique_lock，因为 wait 内部要自动解锁和重新加锁

6. **什么是虚假唤醒？怎么解决？**
   - 线程没有收到 notify 却从 wait 中醒来，是操作系统底层特性
   - 解决：醒来后重新检查条件，用 while 循环而不是 if，或用带谓词的 wait

7. **notify_one 和 notify_all 的区别？**
   - notify_one：唤醒一个等待线程，线程池一般用这个
   - notify_all：唤醒所有等待线程，关闭线程池时用这个

8. **生产者-消费者模型怎么实现？**
   - 共享队列 + mutex 保护 + condition_variable 通知
   - 生产者：加锁放任务 → 解锁 → notify_one
   - 消费者：加锁 wait（队列非空或结束）→ 取任务 → 解锁 → 执行任务

### 线程池

9. **线程池的原理？为什么要用线程池？**
   - 原理：提前创建固定数量的线程，反复复用，任务队列存放待执行任务，工作线程循环取任务执行
   - 为什么：避免频繁创建/销毁线程的开销，控制并发线程数，防止系统过载

10. **线程池的核心组件？**
    - 任务队列（std::queue + std::function）
    - 工作线程数组（std::vector<std::thread>）
    - 互斥锁（保护任务队列）
    - 条件变量（任务来了唤醒工作线程）
    - 停止标志（优雅退出）

11. **线程池怎么优雅退出？**
    - 设置 stop_=true（加锁）
    - notify_all 唤醒所有等待的工作线程
    - 工作线程检查 stop_ && tasks_.empty() 时退出
    - 主线程 join 等待所有工作线程退出
    - 队列里剩余的任务会执行完再退出（优雅退出）

12. **std::function 的作用和原理？**
    - 作用：包装任意可调用对象（函数、lambda、仿函数、bind 表达式）
    - 原理：类型擦除（type erasure），用虚函数调用包装的对象
    - 小对象优化（SSO）：小 lambda 直接存在对象内部，大的才堆分配

13. **std::atomic 和 mutex 的区别？**
    - std::atomic：原子操作，无锁，性能高，只支持简单类型和操作（++、--、load、store）
    - mutex：互斥锁，可保护任意临界区，性能略低，可能阻塞
    - 简单计数用 atomic，复杂临界区用 mutex

14. **单例模式的线程安全实现？**
    - C++11 局部静态变量：`static T instance;` 保证初始化线程安全
    - 双重检查锁定（DCLP）：需要 atomic 和 memory_order
    - 推荐用局部静态变量，最简单

### 集成到服务器

15. **单 Reactor + 线程池模型的工作流程？**
    - 主线程（Reactor）：epoll_wait 事件循环，accept 新连接，recv 数据，解析请求，把业务处理任务提交给线程池
    - 工作线程：从线程池取任务，执行业务处理（读文件、查数据库、构造响应），send 响应
    - 优点：IO 和业务分离，主线程不被慢操作阻塞

16. **工作线程为什么不能操作 eventloop？**
    - eventloop 不是线程安全的，epoll 操作（epoll_ctl）和 epoll_wait 同时进行会数据竞争
    - 工作线程只能做业务处理和 send，不能操作 epoll
    - 如果需要修改 fd 的监听事件，要通过 runInLoop 机制丢回主线程执行（M5/M6 内容）

17. **为什么提交任务前要从 epoll 移除 fd？**
    - 防止工作线程处理期间主线程又收到这个 fd 的新数据，导致同一个 fd 有多个任务并发处理
    - 并发处理同一个 fd 会导致 send 响应顺序混乱、数据竞争
    - 移除后主线程不会再收到这个 fd 的事件，工作线程可以安全处理
