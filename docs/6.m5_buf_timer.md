## 1. 为什么要做 M5

### M4 的问题

M4 的线程池版本有两个致命问题：

**问题1：send 不处理缓冲区满**
```cpp
send(fd, buf, n, 0);  // 直接 send
```
当 socket 发送缓冲区满时，send 返回 -1，errno = EAGAIN。数据直接丢失，高并发压测下大量回包丢失。

**问题2：没有非活动连接清理**
客户端建立连接后不发数据，服务器永远等下去，fd 资源泄漏。

### M5 要解决什么

| 子问题 | 解决方案 |
|--------|----------|
| send 缓冲区满 | channel 内部维护 write_buf_，满了就注册 EPOLLOUT |
| 非活动连接 | 红黑树定时器，15 秒无操作自动关闭 |
| 工作线程不能直接操作 epoll | runInLoop + eventfd，任务丢回主线程执行 |
| g_http_requests 多线程访问 | mutex 加锁 |

## 2. 第一步：updatechannel 区分 ADD/MOD

### 2.1 原始问题（M2 遗留 bug）

M2 的 updatechannel 永远只做 `EPOLL_CTL_ADD`：
```cpp
// ❌ 错误版本
void updatechannel(channel* ch) {
    epoll_ctl(epfd_, EPOLL_CTL_ADD, ch->getfd(), &ev);
}
```

当 fd 已经在 epoll 里，再次调用 ADD 会返回 `EEXIST`（文件已存在），程序直接 exit(1) 崩溃。

### 2.2 epoll_ctl 的三个操作

| 操作 | 作用 | 使用场景 |
|------|------|----------|
| EPOLL_CTL_ADD | 把 fd 加入 epoll | 新连接、刚 accept 的 connfd |
| EPOLL_CTL_MOD | 修改 fd 监听的事件 | 从 EPOLLIN 改成 EPOLLIN\|EPOLLOUT |
| EPOLL_CTL_DEL | 把 fd 从 epoll 移除 | 连接关闭 |

### 2.3 正确写法

```cpp
void updatechannel(channel* ch) {
    int fd = ch->getfd();
    struct epoll_event ev;
    ev.events = ch->getevents();
    ev.data.ptr = ch;

    int op;
    if (channels_[fd] == nullptr) {
        op = EPOLL_CTL_ADD;     // 还没加入过，走 ADD
    } else {
        op = EPOLL_CTL_MOD;     // 已经在 epoll 里，走 MOD
    }

    if (epoll_ctl(epollfd_, op, fd, &ev) == -1) {
        perror("epoll_ctl");
        return;  // 不要 exit！一个连接错误不能搞垮整个服务器
    }
    channels_[fd] = ch;
}
```

**关键判断**：`channels_[fd] == nullptr` 说明这个 fd 还没加入 epoll，走 ADD；否则走 MOD。

### 2.4 deletechannel 也要改

```cpp
void deletechannel(channel* ch) {
    epoll_ctl(epollfd_, EPOLL_CTL_DEL, ch->getfd(), nullptr);
    channels_[ch->getfd()] = nullptr;  // 别忘了置空
}
```

**注意**：close(fd) 之后内核自动把 fd 从 epoll 移除，此时再调 DEL 会返回 ENOENT，这是正常的，不能 exit。

## 3. 第二步：channel 发送缓冲区 + EPOLLOUT

### 3.1 为什么需要发送缓冲区

socket 的发送缓冲区大小有限（通常默认 16KB~64KB）。当要发的数据比缓冲区大，或者对方接收慢时：

```
应用层 send() → 内核发送缓冲区 → 网卡 → 对方接收缓冲区
                  ↑
              如果这里满了，send 返回 -1, errno=EAGAIN
```

此时数据发不出去，但不能丢。正确做法：
1. 把没发完的数据存到 channel 内部的 `write_buf_`
2. 注册 EPOLLOUT 事件（告诉 epoll：等发送缓冲区有空位了通知我）
3. 缓冲区有空位时，epoll 返回 EPOLLOUT，在 handle_write() 里继续发

### 3.2 channel 新增成员

```cpp
class channel {
    // ... 原有成员 ...
private:
    std::string write_buf_;   // 发送缓冲区
    bool close_after_write_ = false;  // 发完是否关闭连接
    std::function<void()> close_callback_;  // 发完后的回调
};
```

### 3.3 write() 函数：尝试发送

```cpp
void write(const std::string& data) {
    write_buf_ += data;  // 先追加到缓冲区

    // 尝试直接发
    ssize_t n_sent = ::write(fd_, write_buf_.data(), write_buf_.size());

    if (n_sent > 0) {
        write_buf_.erase(0, n_sent);  // 把发成功的部分删掉
    }

    // 如果没发完（缓冲区还有数据），注册 EPOLLOUT
    if (!write_buf_.empty()) {
        enable_write();  // events_ |= EPOLLOUT，updatechannel
    }

    // 如果全部发完了，且设置了 close_after_write，调用回调
    if (write_buf_.empty() && close_after_write_ && close_callback_) {
        close_callback_();
    }
}
```

### 3.4 handle_write()：EPOLLOUT 就绪时继续发

```cpp
void handle_write() {
    while (!write_buf_.empty()) {
        ssize_t n_sent = ::write(fd_, write_buf_.data(), write_buf_.size());

        if (n_sent > 0) {
            write_buf_.erase(0, n_sent);  // 删掉发成功的
        } else if (n_sent == -1) {
            if (errno == EAGAIN || errno == EWOULDBLOCK) {
                break;  // 缓冲区又满了，等下次 EPOLLOUT
            } else {
                // 出错了，关闭连接
                close(fd_);
                break;
            }
        }
    }

    // 全部发完了
    if (write_buf_.empty()) {
        disable_write();  // 取消 EPOLLOUT 监听！重要
        if (close_after_write_ && close_callback_) {
            close_callback_();
        }
    }
}
```

### 3.5 为什么发完要取消 EPOLLOUT

**这是经典坑**：如果发完数据不取消 EPOLLOUT，epoll 会一直通知你"可写"（因为发送缓冲区几乎总是空的），CPU 100% 空转。

```cpp
void disable_write() {
    events_ &= ~EPOLLOUT;  // 从事件掩码里去掉 EPOLLOUT
    g_loop->updatechannel(this);
}
```

### 3.6 enable_write / disable_write

```cpp
void enable_write() {
    events_ |= EPOLLOUT;   // 加上 EPOLLOUT
    g_loop->updatechannel(this);
}

void disable_write() {
    events_ &= ~EPOLLOUT;  // 去掉 EPOLLOUT
    g_loop->updatechannel(this);
}
```

**位运算**：
- `|=` 加上一个标志位：`0000 | 0010 = 0010`
- `&= ~` 去掉一个标志位：`0010 & ~0010 = 0000`

## 4. 第三步：红黑树定时器

### 4.1 为什么需要定时器

keep-alive 连接会一直保持。如果客户端不发数据也不关闭，服务器的 fd 和内存就一直被占着。需要一个机制：**15 秒没有活动的连接，自动关闭**。

### 4.2 数据结构选择：multimap<time_t, int>

```cpp
std::multimap<time_t, int> timer_map_;
// key: 过期时间点（绝对时间戳，比如 1789119375）
// value: 对应的 fd
```

为什么用 multimap 而不是 map？
- 同一个 expire 时间可能有多个 fd（虽然概率小，但理论上可能）
- multimap 允许 key 重复

multimap 底层是红黑树，按 key（时间戳）自动排序。所以最老的定时器永远在 begin()。

### 4.3 四个核心函数

#### add_timer：新连接加定时器

```cpp
void add_timer(int fd) {
    time_t expire = time(nullptr) + TIMEOUT_SEC;  // 当前时间 + 15秒
    timer_map_.insert({expire, fd});
}
```

#### update_timer：有活动就刷新（延长 15 秒）

```cpp
void update_timer(int fd) {
    // 1. 先删除这个 fd 的所有旧定时器条目
    for (auto it = timer_map_.begin(); it != timer_map_.end();) {
        if (it->second == fd) {
            it = timer_map_.erase(it);  // erase 返回下一个迭代器！
        } else {
            ++it;  // 不删才需要手动 ++it
        }
    }
    // 2. 加一个新的 15 秒后过期的条目
    time_t expire = time(nullptr) + TIMEOUT_SEC;
    timer_map_.insert({expire, fd});
}
```

**for 循环里 erase 的写法（重要语法）**：
```cpp
// ❌ 错误：erase 后 it 失效
for (auto it = v.begin(); it != v.end(); ++it) {
    if (...) v.erase(it);
}

// ✅ 正确：erase 返回下一个有效迭代器
for (auto it = v.begin(); it != v.end();) {
    if (...) {
        it = v.erase(it);  // erase 返回 it 的下一个位置
    } else {
        ++it;
    }
}
```

#### delete_timer：连接关闭时删定时器

```cpp
void delete_timer(int fd) {
    for (auto it = timer_map_.begin(); it != timer_map.end();) {
        if (it->second == fd) {
            it = timer_map_.erase(it);
        } else {
            ++it;
        }
    }
}
```

#### handle_expired：检查超时

```cpp
void handle_expired() {
    time_t now = time(nullptr);
    while (!timer_map_.empty()) {
        auto it = timer_map_.begin();  // 最早过期的在最前面
        if (it->first > now) break;    // 还没过期，后面的更不会过期
        int fd = it->second;
        timer_map_.erase(it);
        close_connection(fd);          // 关闭超时连接
    }
}
```

### 4.4 epoll_wait 加超时

原来 epoll_wait 永久阻塞（最后一个参数 -1），handle_expired 永远不会被调用：

```cpp
// ❌ 永久阻塞，定时器永远不触发
epoll_wait(epfd_, events, MAX_EVENTS, -1);

// ✅ 每秒醒一次，检查定时器
epoll_wait(epfd_, events, MAX_EVENTS, 1000);  // 1000ms = 1秒
handle_expired();  // 醒了就检查一下超时
```

### 4.5 close_connection：完整的关闭流程

```cpp
void close_connection(int fd) {
    channel* ch = channels_[fd];
    if (ch) {
        deletechannel(ch);  // ① 从 epoll 移除
        close(fd);          // ② 关闭 fd
        delete ch;          // ③ 释放 channel
        channels_[fd] = nullptr;
    }
    {
        std::lock_guard<std::mutex> lock(g_http_mutex);
        g_http_requests.erase(fd);  // ④ 清理请求对象
    }
}
```

## 5. 第四步：runInLoop + eventfd + keep-alive

### 5.1 为什么需要 runInLoop

**问题**：工作线程处理完请求后，要把数据发回客户端（ch->write），还要重新注册读事件（updatechannel）。但 epoll 只能在主线程操作！

工作线程直接调 `epoll_ctl` 是**线程不安全**的（epoll 不是线程安全的）。

**解决思路**：工作线程不能直接操作 epoll，那就把"要做的操作"打包成一个任务，丢回主线程，让主线程来执行。

### 5.2 eventfd：跨线程唤醒 epoll

主线程在 `epoll_wait` 里睡觉。工作线程丢了任务进去，怎么叫醒主线程？

**eventfd** 是 Linux 提供的一个进程间通信机制，本质是一个 fd，里面存着一个 8 字节的计数器：

```cpp
// 创建 eventfd
int wakeup_fd_ = eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC);
//                  ↑初始值 0   ↑非阻塞      ↑fork 自动关闭
```

**唤醒原理**：
```
工作线程：write(wakeup_fd_, &one, 8)  → 计数器 +1，wakeup_fd_ 变可读
主线程：epoll_wait 被唤醒 → wakeup_fd_ 就绪 → handle_wakeup
主线程：read(wakeup_fd_, &one, 8)     → 读出计数器值，清零
```

### 5.3 eventloop 新增成员

```cpp
class eventloop {
private:
    int wakeup_fd_;           // eventfd 的 fd
    channel* wakeup_channel_;  // 包装 wakeup_fd 的 channel
    std::vector<std::function<void()>> pending_tasks_;  // 待执行任务队列
    std::mutex mutex_;        // 保护 pending_tasks_
};
```

### 5.4 runInLoop：把任务丢回主线程

```cpp
void runInLoop(std::function<void()> task) {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        pending_tasks_.push_back(task);  // 任务入队
    }
    // 唤醒主线程
    uint64_t one = 1;
    ssize_t n = write(wakeup_fd_, &one, sizeof(one));
}
```

### 5.5 handle_wakeup：主线程被唤醒后执行任务

```cpp
void handle_wakeup() {
    // 1. 读 eventfd，清零计数器（必须读，否则一直触发 EPOLLIN）
    uint64_t one;
    read(wakeup_fd_, &one, sizeof(one));

    // 2. 取出所有待执行任务
    std::vector<std::function<void()>> tasks;
    {
        std::lock_guard<std::mutex> lock(mutex_);
        tasks.swap(pending_tasks_);  // swap 比 move 更快
    }

    // 3. 逐个执行
    for (auto& task : tasks) {
        task();
    }
}
```

**为什么 read 能清零？**
eventfd 的工作方式：read 返回计数器当前值，然后把计数器清零。write 则给计数器加上写入的值。这是内核定义好的语义。

### 5.6 loop() 里注册 wakeup_channel

```cpp
eventloop::eventloop() {
    epollfd_ = epoll_create1(EPOLL_CLOEXEC);
    channels_.resize(MAX_FDS, nullptr);

    // 创建 eventfd
    wakeup_fd_ = eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC);
    wakeup_channel_ = new channel(wakeup_fd_);
    wakeup_channel_->setreadevents();
    wakeup_channel_->setreadcallback([this]() { handle_wakeup(); });
    updatechannel(wakeup_channel_);  // 加入 epoll
}
```

### 5.7 keep-alive 恢复：close_callback 不再关闭连接

M4 里 close_callback 是关闭连接。M5 里改成：发完响应后，重新注册读事件，继续保持连接。

```cpp
ch->set_close_callback([fd, req, ch]() {
    // 用 runInLoop 把"重新注册读事件"丢回主线程
    g_loop->runInLoop([fd, req, ch]() {
        // ① 检查 ch 是否还有效（竞态保护）
        if (g_loop->get_channel(fd) != ch) {
            delete req;
            return;
        }
        req->reset();              // 重置解析状态
        ch->setreadevents();       // 重新监听读事件
        g_loop->updatechannel(ch);
        g_loop->update_timer(fd);   // 刷新定时器

        // ② 粘包处理：检查缓冲区里还有没有完整请求
        if (req->parse("", 0)) {
            g_loop->deletechannel(ch);  // 处理期间先从 epoll 移除
            g_pool->submit([fd, req, ch]() {
                process_request(fd, req, ch);
            });
        }
    });
});
```

### 5.8 完整数据流（keep-alive 模式）

```
1. 客户端发请求
   ↓
2. 主线程 handle_read：recv → parse → 有完整请求
   → deletechannel（从 epoll 移除）
   → 提交线程池
   ↓
3. 工作线程 process_request：
   → 构造 HTTP 响应
   → ch->write(response)
   → 发完后调用 close_callback
   ↓
4. close_callback 里 runInLoop(任务)
   → 工作线程写 eventfd，唤醒主线程
   ↓
5. 主线程被 eventfd 唤醒 → handle_wakeup
   → read eventfd 清零
   → 执行任务：
     - req->reset()
     - updatechannel（重新注册 EPOLLIN）
     - update_timer（刷新 15 秒）
     - parse("", 0) 检查粘包
   ↓
6. 连接保持，等下一次客户端数据
```

## 6. 第五步：g_http_requests 加互斥锁

### 6.1 为什么要加锁

`g_http_requests` 是全局的 `unordered_map<int, Httprequest*>`。

访问点：
- **主线程**：handle_read 里 find、close_connection 里 erase
- **工作线程**：process_request 里通过 req 指针访问（不直接操作 map，但 close_connection 里的 erase 可能在主线程）

如果两个线程同时操作 unordered_map（比如一个 find 一个 erase），unordered_map 的内部结构可能损坏，导致崩溃。

### 6.2 正确写法

```cpp
std::mutex g_http_mutex;  // 全局互斥锁

// 读（find）
{
    std::lock_guard<std::mutex> lock(g_http_mutex);
    auto it = g_http_requests.find(fd);
}
// 锁在花括号结束时自动释放（RAII）

// 写（erase / insert）
{
    std::lock_guard<std::mutex> lock(g_http_mutex);
    g_http_requests.erase(fd);
}
```

### 6.3 std::lock_guard 的用法

```cpp
{
    std::lock_guard<std::mutex> lock(mutex);  // 构造时加锁
    // ... 临界区 ...
}  // 析构时自动解锁（即使抛异常也会解锁）
```

**为什么不用 lock()/unlock()？**
- 如果临界区里抛异常，unlock() 不会执行，锁永远不释放 → 死锁
- lock_guard 是 RAII，构造加锁、析构解锁，异常安全

## 7. 踩坑汇总（按出现顺序）

### 坑1：updatechannel 永远只 ADD
- **现象**：第二次修改事件时 epoll_ctl 返回 EEXIST，程序 exit
- **原因**：没区分 ADD 和 MOD
- **修复**：用 channels_[fd] == nullptr 判断走哪个分支

### 坑2：deletechannel 失败直接 exit
- **现象**：连接关闭后，再次 DEL 返回 ENOENT，程序崩
- **原因**：close(fd) 后内核自动从 epoll 移除，再 DEL 当然找不到
- **修复**：只打印 perror，不 exit

### 坑3：send 不处理 EAGAIN
- **现象**：高并发压测下回包丢失
- **原因**：发送缓冲区满时 send 返回 -1，数据直接丢
- **修复**：加 write_buf_，没发完的存进去，注册 EPOLLOUT

### 坑4：发完数据不取消 EPOLLOUT
- **现象**：CPU 100% 空转
- **原因**：EPOLLOUT 一直就绪（发送缓冲区几乎总是空的）
- **修复**：write_buf_ 清空后 disable_write()

### 坑5：for 循环里 erase 迭代器
- **现象**：段错误 / 未定义行为
- **错误写法**：
  ```cpp
  for (auto it = v.begin(); it != v.end(); ++it) {
      if (...) v.erase(it);  // erase 后 it 失效了！
  }
  ```
- **正确写法**：
  ```cpp
  for (auto it = v.begin(); it != v.end();) {
      if (...) it = v.erase(it);  // erase 返回下一个迭代器
      else ++it;
  }
  ```

### 坑6：g_loop 未声明（全局变量声明顺序）
- **现象**：`g_loop was not declared in this scope`
- **原因**：channel 类的成员函数里用了 g_loop，但 g_loop 声明在 channel 类之后
- **修复**：把 g_loop 的声明移到类定义之前，或者用指针前置声明

### 坑7：接受连接后程序直接退出（段错误）
- **现象**：accept 后 segmentation fault
- **原因**：close_callback 的 lambda 捕获了 ch，发完后 delete ch，但 close_callback 在 delete ch 之后才被调用
- **修复**：调整顺序——先 close(fd)、delete req、erase map，最后 delete ch

### 坑8：channels_[fd] 越界断言失败
- **现象**：`Assertion '__n < this->size()' failed`，Aborted
- **原因**：close_callback 的 runInLoop 任务捕获了 ch，但 ch 在任务执行前就被 handle_read 的关闭分支 delete 了。任务执行时 ch->getfd() 返回垃圾值，channels_[垃圾值] 越界
- **竞态时序**：
  ```
  工作线程：close_callback → runInLoop(任务) → 写 eventfd
  主线程还在处理 connfd 关闭 → delete ch
  主线程处理 eventfd → 执行任务 → 访问已 delete 的 ch → 崩溃
  ```
- **修复**：任务开头加检查
  ```cpp
  if (g_loop->get_channel(fd) != ch) {
      delete req;
      return;
  }
  ```

### 坑9：定时器重复添加
- **现象**：timer_count 越来越大，同一个 fd 有多个定时器条目
- **原因**：close_callback 里误用了 add_timer（只新增不删除）
- **修复**：改成 update_timer（先删旧的再加新的）

### 坑10：浏览器 favicon.ico 多连接
- **现象**：明明只开了一个网页，却有三个 fd（6、7、8）
- **原因**：浏览器自动请求 /favicon.ico，建立第三个连接
- **结论**：不是 bug，是正常行为

### 坑11：高并发压测时大量连接同时关闭，channels_[fd] 越界
- **现象**：mul_client 压测到 ~10000 连接后，客户端报 `Too many open files`，服务器端大量打印 `delete_timer`，然后 `Assertion '__n < this->size()' failed`，Aborted
- **原因**：大量短连接同时断开时，`timer_map_` 里可能残留了已经无效的 fd（竞态条件导致 fd 被 close 后重新分配，timer_map_ 里的 fd 和实际 channel 不同步）。`close_connection(fd)` 里 `channels_[fd]` 访问了越界的 fd
- **时序**：
  ```
  1. 10000 个短连接同时建立
  2. 客户端断开（Too many open files）
  3. 服务器端大量 EPOLLIN 触发，handle_read 里 n==0，逐个关闭
  4. 同时定时器也在触发，handle_expired 里 close_connection
  5. 某个 fd 已经被 close 并重新分配给新连接，但 timer_map_ 里还是旧值
  6. channels_[fd] 访问到无效位置 → 越界断言失败
  ```
- **修复**：close_connection 和 handle_expired 里加 fd 范围保护
  ```cpp
  void close_connection(int fd) {
      if (fd < 0 || fd >= (int)channels_.size()) {
          std::cerr << "close_connection: 无效 fd=" << fd << std::endl;
          return;
      }
      // ...
  }
  ```
- **教训**：高并发下，任何"全局 map 按 fd 索引"的代码都要加范围检查。fd 是可以被重新分配的，不能假设 timer_map_ 里的 fd 一定有效

## 8. 面试问答

### Q1：为什么需要发送缓冲区？直接 send 不行吗？

答：直接 send 在高并发下会丢数据。当发送缓冲区满时 send 返回 EAGAIN，数据没发出去。正确做法是把没发完的数据存到用户态缓冲区，注册 EPOLLOUT，等缓冲区有空位了内核通知你再继续发。

### Q2：EPOLLOUT 为什么发完要取消？

答：因为发送缓冲区几乎总是空的（只要你发得出去），EPOLLOUT 就一直就绪。不取消的话 epoll_wait 立即返回，CPU 100% 空转。这是 epoll 的经典坑——只在确实需要写的时候才监听 EPOLLOUT。

### Q3：定时器为什么用红黑树（multimap）？

答：需要按过期时间排序，快速找到最早过期的连接。红黑树插入/删除/查找都是 O(log n)，而且自动排序，begin() 就是最老的定时器。

### Q4：为什么用 eventfd 唤醒主线程？

答：epoll_wait 阻塞时，工作线程有任务要主线程执行，需要唤醒它。eventfd 是专门的跨线程唤醒机制，把 eventfd 加入 epoll，工作线程 write 一下，主线程的 epoll_wait 就返回了。比 pipe 更轻量（只占一个 fd）。

### Q5：runInLoop 解决了什么问题？

答：epoll_ctl 不是线程安全的，工作线程不能直接操作 epoll。runInLoop 把"要做的操作"打包成 lambda，丢回主线程的任务队列，工作线程写 eventfd 唤醒主线程，主线程在 handle_wakeup 里执行这些任务。所有 epoll 操作都在主线程完成。

### Q6：close_callback 的竞态条件是什么？怎么解决的？

答：工作线程发完数据后调 close_callback，close_callback 里用 runInLoop 把"重新注册读事件"丢回主线程。但此时客户端可能已经关闭了连接，主线程的 handle_read 里已经 delete 了 ch。任务执行时访问已 delete 的 ch 就崩溃。

解决：任务开头检查 `get_channel(fd) != ch`，如果 ch 已经不在 channels_ 里了，说明被 delete 了，直接 return。

### Q7：epoll_ctl 的 ADD 和 MOD 有什么区别？

答：ADD 是把新的 fd 加入 epoll；MOD 是修改已经在 epoll 里的 fd 监听的事件。如果对已经在 epoll 里的 fd 调 ADD，会返回 EEXIST 错误。所以 updatechannel 要先判断这个 fd 是否已经在 epoll 里。

### Q8：epoll_wait 的超时参数设多少？为什么？

答：设 1000ms（1 秒）。因为要定期检查定时器，超时参数设为 -1（永久阻塞）的话，定时器永远不会触发。设 1 秒，每秒醒一次检查有没有过期的连接。精度不需要太高，1 秒足够。
